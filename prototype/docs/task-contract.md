# 需求、审批与交付约定

## 简化入口

创建需求只需需求描述，可选关联功能和来源。没有足够信息时状态为“待澄清需求”，不生成空泛完整合同，也不生成十五类空影响项。

## 候选与影响

开发/编辑角色可以基于当前批准规则提出候选。Task 保存规则 ID、基线版本、判断行、条件差异和输入业务含义，不复制完整规范。

影响候选只来自现有知识的明确关系，标明“未执行真实仓库调查”。人工可记录需要修改、无需修改、转其他 Task 或待确认；标准调查范围只在需要完整性审查时展开。

## 真实审批链

1. 开发提出候选并记录模拟实现/测试。
2. 业务 Owner 批准或拒绝；拒绝不生成草稿。
3. 批准调用 `DefineRule`，进入现有 Change Set。
4. 编辑/Owner 提交 Change Set，Owner 发布 Baseline。
5. 发布原子更新 KnowledgeChange、Manifest、Task 知识状态及知识类影响项。
6. 关联 Task 复核正式知识契约。
7. 必要影响、旧路径人工检查、实现、测试、知识和版本均闭合后，由验收 Owner 完成模拟 Task。

任务状态区分：待澄清、业务待批准、知识草稿待审核、知识已发布待契约复核、可以验收、已完成。模拟完成只证明原型内部规则闭合。

## 原型写权限

- reader / external：只读，无业务写入和敏感导出。
- developer：创建需求、候选、影响记录、模拟交付和契约。
- editor：可编辑知识草稿和提交 Change Set。
- owner：批准/拒绝业务决定、发布 Baseline、最终验收。
- admin：原型管理、完整备份及全部模拟权限。

这是前端模型一致性检查，不是企业安全机制。
