# Business Atlas V9.3 核心业务认知与交付闭环评审

日期：2026-11-16  
结论：**READY FOR CONTROLLED PILOT。V9.3 已把“知识条目管理”纠正为可解释、可验证、可演进的项目共同认知；交互与领域语义可作为正式产品开发纵切依据，但不等于生产上线就绪。**

## 1. V9.2 的核心不足

V9.2 已有统一实体/断言、基线、权限、局部图和任务契约，但核心阅读仍以“目的 → 关联规则 → 技术实现 → 来源”的对象组织为主：

- 功能页能列出规则，却不能优先解释具体条件下怎样判断、产生什么结果。
- 目标规范、代码实际行为和技术机制没有形成正式对照，容易把现状误读成需求。
- 旧模拟器以枚举默认值和首条命中为主，缺失输入、未确认优先级、未知条件和默认分支不够严格。
- Scenario 的 Flow-only Rule 可能遗漏，阶段出现 `GROUP-undefined`，同阶段不同条件边会被去重，状态过滤恒真。
- Task 主要记录标题、状态、根知识和契约，未明确目标行为变化、保留约束、完整影响和知识交付。
- Task、Issue、Delivery、首页等仍存在原始集合读取和草稿污染风险。

V9.3 没有增加“业务决策契约”导航或第二知识库，而是修正既有模型、投影、阅读和闭环。

## 2. 统一知识模型怎样修正

所有能力继续使用 Entity、Assertion、Rule、Flow、Scenario、Source、Schema Registry、Read Context、Change Set 和 Baseline。新增仅是兼容语义字段与普通知识类型：

- `factKind / semanticRole / decisionRef / implementationEvidenceRefs`。
- `BusinessCase`：正、反、边界、未知和回归案例。
- `ObservedBehavior`：对象、版本、环境、方式、输入、实际输出、可信度和适用范围。
- Task 的 `semanticContract / impactInvestigation / delivery`。
- Decision Record、KnowledgeChange 与 Delivery Manifest 关联记录。

目标规范、当前观察、技术机制、任务和验收共享同一权威事实，不复制到不同知识库。

## 3. 完整业务决策链怎样形成

Feature/Scenario/Rule 默认先回答：为什么存在、谁使用、何时触发、依据什么判断、各分支什么结果、异常和默认怎样处理、实现是否符合。

决策语义覆盖 Context、Inputs、Preconditions、Evaluation、Priority、Branch、Outcome、Default、Exception、Evidence。默认使用“条件—判断—结果”表；复杂 Scenario 先显示真实七阶段和当前阶段，再展开完整流程。

规则收集统一覆盖直接关联、Action 所受规则、Flow 节点和条件边、显式状态 Guard；同时按根 Feature 的真实 Action 限定范围，避免登记功能误收整个处置流程的规则。

## 4. 目标、行为与机制怎样区分

- **Target Specification**：批准规则版本、业务目的、适用范围、来源和 Owner。
- **Observed Behavior**：特定版本/环境的观察输入、实际输出、方式和可信度。
- **Implementation Mechanism**：API、组件、SQL、配置、事件和调用链。

符合性单独计算：一致、不一致、未验证、缺少目标、缺少观察、版本需复核、部分适用和来源冲突。观察版本与当前代码不同会要求重新核验，技术机制绝不自动批准目标。

搜索黄金样本保持：123 与 1234 的当前结果不同、全文词元机制存在、目标匹配规则未确认。参数样本只执行已批准的存在性，未知比较字段不会被补齐。

## 5. Rule 怎样利用案例验证

确定性评估器只执行明确条件：equals、notEquals、contains、startsWith、exists、notExists、greaterThan、lessThan、in、all、any。

每个结果包含前提、每条规则行、条件轨迹、命中分支、结果类型、缺失事实、冲突和来源。未知输入不默认成功，自定义条件不默认 true；无批准默认分支时不猜测结果。多行冲突不默认第一条/最新/最窄优先。

案例固定 `ruleId + version`，验证不一致形成 `CASE_CONFLICT`，不会修改规则迎合示例。相同输入、权限、适用上下文和基线产生一致判断。

## 6. Task Semantic Contract 怎样生成、维护和验收

用户从“任务与问题 → 新建需求 / 变更任务”只描述业务目标、问题、功能、目标和来源。系统通过 Read Context 组织批准规则、观察、实现和未决问题。

候选目标保存“批准规则版本 + 判断行差异 + proposed revision”，不是完整规范副本。新增、修改、删除和保持不变分别展示；其他判断行、默认和异常进入保留约束。

完整行为变化使用完整合同；文案、样式和内部重构使用简化合同，但仍需保留行为和验证。正式验收检查目标、影响、实现、测试、旧路径、知识、版本和批准，Task 状态不能替代这些检查。

## 7. 系统影响调查怎样组织

调查覆盖功能、规则、调用方、前端、API、后端、数据库、参数、事件、配置、测试、旧路径、兼容、部署迁移和知识。

关系遍历只生成候选，排除会把整个项目都变成影响的引用/归属扩展。每项记录路径、关系语义、证据、状态、决定、进度和理由：`required / potential / no-change / deferred / unknown`。

无需修改必须有依据，转交必须有关联 Task，未知和必要项未完成会阻断完整交付。重复适配器、无效兼容、旧路径和死代码进入主动收敛调查，不以“用户没点名”为保留理由。

## 8. 开发知识怎样持续回写

与 V1.2 对齐：

- PR 关联候选知识。
- 合并后生成 Knowledge Delivery Manifest。
- 测试绑定代码版本和案例。
- KnowledgeChange 独立进入治理与 Baseline。
- 部署版本与知识版本对账。
- Task 可继续发起 Issue、Feedback、Proposal、Change Set 或架构决策。

六类版本分别显示：需求、批准业务基线、实现代码、测试版本、部署版本、知识提案/清单批准状态。原型明确标注模拟 PR、测试和 Manifest，不冒充真实工程系统。

制造模拟交付实际显示“实现完成 · 知识待审批”；点击完成会被阻止，因为知识提案和批准基线尚未完成。

## 9. AI 自主判断与业务批准边界

Agent 可调查源码、调用链、技术重复、未使用路径和潜在影响，提出架构收敛、技术测试、知识缺口和变更提案；授权范围内不改变业务语义的工程决定可独立记录。

业务规则、客户可见行为、重要默认值、数据删除、关键权限和不可逆迁移必须由 Owner 决策。搜索待决问题提供精确/前缀/子串的业务结果、兼容影响和推荐依据，但 `approval:null` 前推荐不生效。

## 10. 图形与权限缺陷怎样修复

- 阶段节点不再按不存在的 `typeId` 聚合，七阶段身份独立。
- 不同条件边按原 ID 保留，完整 Flow 可展开 14 条边，REWORK 回流保留。
- 未确认状态转移只在探索中标记显示，正式视图排除。
- 执行、约束、依赖、实现和读写采用不同标签/样式，不把依赖画成业务流程。
- Flow 引用逐节点授权，受限引用不会泄露，正式契约会阻断而非误报完整。
- Flow 语义指纹排除布局；纯布局不触发任务失效，真实节点/边变化会触发。
- Task、Issue、首页、交付选择器、决策评估、导出统一授权；首页批准视图不读草稿介绍。
- 非管理员备份不再导出整个 store；业务决策和 Task 导出重新授权。

## 12. 仍未解决的风险

- 权限是前端模拟，不能作为生产安全边界；真实写授权、认证和服务端审计仍需实现。
- 通用流程级多步状态机模拟尚未完成，当前主要是单 Rule 评估与真实 Flow 阅读。
- 自由文本 Guard 需要人工治理成明确规则引用，不能自动形式化。
- 影响调查在真实项目中的召回率、误报率和隐式调用覆盖需要试点数据。
- 不包含真实后端、数据库、多人并发、仓库同步、MCP/LLM、真实编程 Agent 或部署。
- localStorage 有容量和清理风险；复杂大图仍需更完整的导航/编辑能力。
- 浏览器工具验收不是独立真人认知效率研究。

## 13. 能否作为正式产品开发依据

**可以，建议进入受控真实项目试点。** V9.3 已形成可实现的领域不变量、负向约束、页面结构、读模型、评估协议、Task 合同、交付状态和回归样本。

正式开发应优先纵切：服务端身份与权限 → 统一知识/版本存储 → 决策阅读与评估 → Task 影响和 V1.2 交付 → 真实 Agent/仓库接入。不得把“原型验收通过”解释为生产性能、安全、并发、真实用户理解效率或全量影响召回已经证明。
