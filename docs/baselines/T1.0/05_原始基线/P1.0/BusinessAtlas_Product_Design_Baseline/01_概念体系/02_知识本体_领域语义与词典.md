# 02｜项目知识本体、领域语义与核心概念词典

状态：R（候选规范）。本文件定义概念及边界，不要求所有概念都变成表、实体类型或 UI。适用于平台管理的任意软件项目；项目自己的领域词汇须作为知识资产长期维护。

## 1. 四个不可混淆的层次

| 层次 | 问题 | 例子 | 不是什么 |
|---|---|---|---|
| 认知框架 Taxonomy | 从哪些角度认识项目 | 业务认知、系统认知 | 不是物理数据模型 |
| 知识本体 Ontology | 存在哪些概念、关系与约束 | 规则约束行为，字段映射业务属性 | 不是平面标签目录 |
| 领域模型 Domain Model | 一个具体业务领域实际上有哪些概念及关系 | CPQ 中的报价单、配置、非标参数 | 不是数据库表结构 |
| 认知呈现 Representation | 为解决某个认知任务怎样组织内容 | 功能页的需求、规则、设计三个 Tab | 不是新的事实库 |

五维框架是对观察角度的分类；本体定义可以被描述的知识和它们如何连接；语义原语是表达这些概念的基础；具体项目的知识是它们的实例；内容模板只是面向审阅和阅读的组合方式。不应将所有词典词条注册成独立对象。

## 2. 五大认知维度（沿用既有框架）

### A 项目认知：为什么做、边界在哪里

| 概念 | 英文 | 语义与边界 |
|---|---|---|
| 项目 Project | Project | 独立认知、权限、责任与变更边界。不同项目同名知识不是同一对象。 |
| 问题域 | Problem Domain | 需要解决的问题空间，而非系统结构。 |
| 业务领域、子域 | Domain / Subdomain | 具有相对一致业务目标及语义的范围；可多层分解。 |
| 产品愿景、业务目标 | Vision / Business Goal | 想要的未来状态与可评价的业务结果。 |
| 利益相关者 | Stakeholder | 影响目标、决策、使用或承担后果的人/组织。 |
| 需求 | Need | 问题、机会或限制；未澄清的意图不能直接成为已批准功能。 |
| 项目范围 | Scope | 应负责与不负责的能力、组织、环境和约束。 |
| 业务能力 | Business Capability | 业务组织能完成的事情；不必等于单一软件功能。 |
| 软件功能 | Feature | 软件向参与者提供具有明确结果的能力，承载阅读组合。 |
| 价值、成功标准 | Value / Success Criterion | 为什么值得做，以及如何判断目标实现。 |

### B 业务认知：应该怎样判断、怎样发生

| 概念 | 英文 | 语义与边界 |
|---|---|---|
| 领域知识 | Domain Knowledge | 领域语言、对象、专业业务规律、经验、政策、行动和结果的集合。不是一个需要重复保存的总实体。 |
| 统一语言 | Ubiquitous Language | 人和 Agent 共同使用的业务词汇，含明确概念、语境、别名与约定。 |
| 语义上下文 | Semantic Context / Bounded Context | 同一术语具有一致意义的适用边界。不同业务范围中的“客户”可分别定义。不是强制微服务。 |
| 领域术语 | Term | 指称概念的语言表达；一个概念可有多个别名。 |
| 领域概念 | Concept | 对一类业务事物、性质或含义的定义，如“匹配”。比技术名称稳定。 |
| 业务对象 | Business Object | 业务作用于的对象类型，如报价单。区别对象定义与一条具体报价记录。 |
| 业务属性 | Business Attribute | 对象具有的业务含义，如参数名称是否存在。可以由字段、配置或推导结果承载。 |
| 参与者、职责 | Actor / Responsibility | 谁发起、判断、负责或受到影响；与系统操作者、代码职责区分。 |
| 业务事实 | Business Fact | 有明确对象、条件与时间的陈述；可被核验，不自动意味着规范。 |
| 业务需求 | Business Requirement | 为满足需求而必须达成的结果、能力或约束；回答要什么，不规定不必要的实现。 |
| 业务规则 | Business Rule | 对业务应遵循的判断、限制或推导的明确规定；回答何种条件/依据下应该怎样。 |
| 业务策略 | Policy | 更高层原则，可派生多条规则；不能只有口号。 |
| 不变量 | Business Invariant | 在适用范围内所有允许行为必须维护的约束，如不得把参数应用到其他配置。 |
| 前置/后置条件 | Precondition / Postcondition | 行动允许之前须成立的条件；结束后必须成立的事实。 |
| 判断条件 | Condition | 决策适用或命中的前提；区分缺失、空值和不满足。 |
| 判断依据 | Decision Basis | 用来判定条件的业务事实和属性，包含来源、单位及比较口径。 |
| 比较语义 | Comparison Semantics | “一致、包含、有效、重复”的可判定含义。不能依赖程序员猜测 SQL 操作符。 |
| 规则优先级/冲突 | Priority / Conflict | 多条规则同时适用时怎样处理；未确定优先级则冲突待决。 |
| 默认规则/例外 | Default / Exception | 未命中规则或出现特殊情况的明确处理；未知不是默认拒绝或成功。 |
| 决策 | Business Decision | 按规则和事实得到的业务处理判定；与批准设计的治理决策不同。 |
| 决策链 | Decision Chain | 从业务情况、依据、判断到结果的完整推理链；可以用文字或决策表呈现。 |
| 行为 | Business Behavior | 在给定情境下人员/系统的动作及可观察结果；应然行为和实然行为须区分。 |
| 行动 | Action | 具有业务意义的操作；如申请报价、冻结批次。不是函数名。 |
| 业务事件 | Business Event | 已发生且对业务有意义的变化；区别操作意图和结果事件。 |
| 场景 | Scenario | 某个背景、输入与参与者下的行为实例类型。 |
| 用例 | Use Case | 某参与者通过系统达成目标的交互，含替代路径。 |
| 流程 | Process / Flow | 行动与决策之间有依据的顺序、条件分支、回流和终点。无需绘图。 |
| 业务状态 | State | 对象在生命周期中的业务情况。 |
| 状态转移 | Transition | 由行动/事件触发、受前提约束的状态变化。 |
| 异常及补偿 | Exception / Compensation | 非正常路径与先前动作已产生结果时的业务恢复语义。 |
| 案例 | Business Case / Example | 此处专指给定输入、上下文、预期或观察结果的业务例子，不是商业论证。 |

### C 系统认知：怎样实现、怎样运行与维护

| 概念 | 英文 | 语义与边界 |
|---|---|---|
| 功能需求 | Functional Requirement | 软件必须提供的可观察能力/行为；由业务需求派生，含接口等。 |
| 质量需求 | Quality Requirement | 性能、安全、可靠性、可维护性等可验证要求。不是简单写“高性能”。 |
| 技术约束 | Technical Constraint | 设计和实现必须满足的限制、标准或环境。 |
| 设计 | Solution Design | 选择怎样满足规范的方案、职责分配、交互、数据行为、错误及取舍。不是已实现证明。 |
| 系统、模块、组件 | System / Module / Component | 具有明确职责和边界的工程组成，允许不同粒度。 |
| 架构职责与接口契约 | Responsibility / Interface Contract | 谁承担什么行为、怎样提供与消费能力，什么不能移动或改变。 |
| 架构决策 | ADR / Design Decision | 经论证选择某方案、理由、后果与条件。不是日常状态记录。 |
| 逻辑数据模型 | Logical Data Model | 数据概念、业务关系、基数及约束。 |
| 技术数据模型 | Physical Data Model | 实际表、文档、字段、类型、索引等。 |
| 语义映射 | Semantic Mapping | 业务属性/概念与技术字段、表达式、API语义之间的有版本关系。 |
| 实现机制 | Implementation Mechanism | 真实代码、SQL、配置、组件及调用如何实现行为。 |
| 技术操作 / 数据流 | Operation / Data Flow | 调用、转换、读取、写入、事务；不是自动推导出的业务先后关系。 |
| 观察行为 | Observed Behavior | 特定版本和条件下实际观察到的输入/输出/状态；不同于应然。 |
| 符合性 | Conformance | 某观察或实现证据是否满足给定规范；需要限定版本、范围和证据。 |
| 测试、验收 | Test / Acceptance | 用例、预期、执行结果、验收决策分开；案例不是执行通过证明。 |
| 构建、发布、部署 | Build / Release / Deployment | 工程制品产生与部署环境的版本关系；不与知识批准合并。 |
| 运维知识 | Operational Knowledge | 环境、资源依赖、故障、日志、告警、恢复与 runbook。 |
| 安全与权限 | Security / Authorization | 访问边界、策略、角色、风险、敏感信息与控制依据。 |
| 工程规范、技术债 | Engineering Standard / Debt | 长期约束与未完成维护问题。 |

### D 知识资产：为什么知道、可信到什么范围

| 概念 | 含义 |
|---|---|
| Knowledge Unit 知识单元 | 能独立指称、维护和审核的一项知识；原描述、结构化事实和展示不能各自为权威。 |
| Assertion 断言 | 对事实、属性、关系或规则的有语义陈述。一个知识单元可包含多个断言。 |
| Source 来源 | 信息出自何种材料或人员，具备明确身份、版本和定位。 |
| Evidence 证据 | 能支持/反驳具体断言的依据；与原始来源、引用片段、观察方法关联。 |
| Provenance 溯源 | 知识如何被人或工具产生、转换与核验。 |
| Observation / Inference | 观察为直接依据，推断为根据其他事实得出；推断可证伪。 |
| Assumption 假设 | 临时接受以推进分析的前提，不是权威事实。 |
| Knowledge Gap / Conflict | 缺少必要知识，或多个陈述不相容；与无权看到和不适用区分。 |
| Applicability 适用性 | 在具体组织、角色、环境、业务类型、版本和生效时间下是否适用。 |
| Fact Kind / Verification | 事实性质（应然、观察、决策、推断等）与核验状态；与批准、可见性独立。 |

### E 协作治理：怎样持续开发并更新认知

| 概念 | 含义 |
|---|---|
| Proposal 知识提案 | 人或 Agent 提交的尚未生效内容、变更理由与依据。 |
| Review / Approval | 评审是检查和提出修改；批准是授权主体对明确修订与适用范围作决定。 |
| Change Set | 一组必须共同修订/核验的关联知识及处置，可作为批准单元。 |
| Revision / Baseline | 单项不可变修订；基线是已发布的明确修订组合，不是时间戳或代码版本。 |
| Decision Record | 问题、候选方案、推荐、理由、决策权、批准版本与后果。 |
| Task / Issue | Task 代表工作目标，Issue 是需要解决的不确定性、冲突或问题。Task 不是知识副本。 |
| Traceability / Impact | 以有语义的关系双向追踪；影响分析提出候选并通过证据确认，不能只靠图遍历。 |
| Change Semantics / Closure | 明确新增、修订、废弃、保持、复核；以目标和保留约束、调查与证据定义交付完成。 |
| Cognitive Baseline / Context | Agent 开始工作可引用的批准知识组合；本次任务按权限和适用性选取的最小足够上下文。 |
| Cognitive Drift | 已确定认知在后续输出/实现中无授权偏离：需求漂移、业务漂移、职责漂移、范围漂移、知识漂移、表达漂移。 |
| Knowledge Debt | 实现或认知变化已发生但知识/证据/批准尚未同步的可跟踪债务。 |
| Cognitive Quality / Completeness | 内容能否满足具体理解和使用任务，何处仍缺失；不是全局知识百分比。 |

## 3. 领域语义是每个项目长期维护的资产

**核心约定：业务名词不是一个技术字段的备注。** 领域语言记录应包含：概念 ID、名称/别名、定义、业务上下文、对象/属性或关系、允许值或单位（适用时）、例子及反例、相关不变量、来源、Owner、核验/批准状态、修订、适用与生效范围。关键语义有歧义时提出问题并保留候选含义，不用 Agent 的常识硬补全。

例（非真实 CPQ 规则）：「参数名称」是某语境的业务属性；`parameterName` 是技术映射，不能仅由字段名推断空值业务含义。「一致」本身也是领域概念，应说明比较对象、键、空值、重复、归一化、大小写和适用语境。某些项不适用可记录理由；未调查不能写不适用。技术字段删掉时概念未必删除，先调查它作为规则判断依据的关系，再选择保留或修改业务语义。

同一术语在两个上下文含义不同，用两个概念身份和明确上下文；可建立 `equivalentTo`、`narrowerThan`、`mappedTo` 等经审核关系，不以名称自动合并。跨项目共享词汇只能显式引用已授权且有版本的定义；本地适用性与映射独立确认，禁止一项全局词汇变动自动更新所有项目规则。

## 4. 通用语义原语与实际建模粒度

原语：实体、属性、类型化关系、断言、条件、行动、事件、状态/转移、时间/顺序、约束、上下文、来源。每种业务知识通过这些原语组合，不规定数据库模式。建议仅把需要独立识别、复用、引用、修订、授权或审核的内容设为知识单元；简单描述、标签、单条案例的输入值可作为所属单元的内部字段。表达模型可声明一个章节为可选。建立新类型前先问：它真的具备新的语义或生命周期吗？若仅为不同阅读布局，使用视图而非新类型。

## 5. 本体演进原则

通用知识类型由平台维护；项目可提出领域扩展，声明父类、定义、允许关系、表达契约、校验约束及兼容规则。扩展先在项目范围内生效，通用化需独立评审。模式修订与业务知识修订独立；旧基线按当时模式解释。拒绝用任意 JSON 字段把未建模事实包装为可推理规则。优先使用现有类型，避免每个名词变成一张页面。
