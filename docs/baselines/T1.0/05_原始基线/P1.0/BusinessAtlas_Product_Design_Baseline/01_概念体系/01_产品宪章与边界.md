# 01｜产品宪章、八套核心机制与边界

状态：P1.0 候选；用户意图标 U，独立设计推荐标 R。概念定义以 02 为准；操作约束见 03–07。

## 1. 产品定义与需要解决的现实问题

Business Atlas 是管理软件项目知识的产品。管理不是简单归档，而是建立和维护一个人与 AI 可以共同引用、理解、判断和修订的项目认知空间。它所管理的对象包括正在开发的其他业务项目，也包括 Business Atlas 自身；每个项目有独立范围、领域语言、权威知识和历史。

研发团队的认知问题通常不是缺少写代码能力。一项需求从业务意图到规则到设计与实现的传递中，信息被省略、混入错误层次、在聊天中失真；成员知道局部却不知道自己不知道什么。接手老项目的人要靠老员工解释，Agent 每个会话重新探索同一逻辑，修改字段时只查直接引用而忽略隐含业务判断，最新一句话覆盖旧规则。最终形成半新半旧的实现，人的注意力耗在纠正细节和维护关系上。

本产品要改变的是工作分工与信息质量：人提出意图、阅读具有判断价值的产出并反馈/审批；AI 调查、形成有根据的候选知识、组织影响、独立提出技术建议；系统保存事实和约束、执行确定性治理，向人展示结果，而不是把复杂性转交给人。

## 2. 正式产品原则（U）

| ID | 原则 | 可观察的产品要求 | 反例 |
|---|---|---|---|
| P-01 | 人的注意力最小化 | 默认只阅读结论、实质差异、需要人决策的事项；证据可深入 | 让人手填几十项关系和状态 |
| P-02 | 一眼理解、不失深度 | 对目的、判断、结果的解释先出现，技术与证据随后可到达 | 先展示对象ID和全部关系 |
| P-03 | 语义层次明确 | 需求、业务规则、实际行为、技术设计不互相冒充 | SQL查询方式充当业务需求 |
| P-04 | 统一认知语法 | 类似业务在不同项目用相同基本语义组织，允许领域特化 | 每个项目一套不相容页面 |
| P-05 | 统一权威事实 | 同一规则有稳定身份，审核后的规范可被人和 Agent 引用 | 每个 Task 复制规则后独立修改 |
| P-06 | 保持历史与不确定性 | 规范、观察、推断、未知、冲突分别可见；旧版本不被覆盖 | 没找到证据就默认不存在 |
| P-07 | 开发即交付知识 | 代码成果与知识成果共同进入验收，持续形成 Self Project | 开发结束再补全项目文档 |
| P-08 | 系统变化的完整影响 | 以目标行为界定任务；主动找旧入口、兼容、职责约束等 | 只动用户点名的两个参数 |
| P-09 | 工程自主、业务授权 | Agent 可在授权内选择等价实现；业务语义和高风险变更由有权人员决策 | 所有技术小事都请示或擅改业务 |
| P-10 | 表达优先于绘图 | 当前原型不实现绘图引擎；文字、表格、案例可完整解释业务 | 因图小而删除分支和规则 |
| P-11 | 同一机制覆盖生命周期 | 老项目反向认知、新项目构建、持续迭代共用模型 | 新老项目各自维护事实库 |
| P-12 | 完整交付不等于一次编码 | 按真实依赖实施，最终覆盖确定范围，不用局部演示替代完成 | 先做一个局部MVP便宣称产品完成 |

## 3. 八套概念机制（R：保持之前的八项，深化其边界）

八项是对设计问题的划分，不是八个物理模块或一级菜单。领域语义是 M1、M2 的重点独立子体系；认知呈现是 M3 的面向用户结果。认知服务是对 M1–M8 的统一能力出口。共同数据、访问、证据及治理规则不可被各自重新定义。

| 机制 | 关键概念 | 输入 | 产物 | 与其他机制关系 |
|---|---|---|---|---|
| M1 知识本体 | 领域知识、认知维度、术语、类型、语义原语 | 软件工程实践、项目对象、领域语言 | 通用类型及领域扩展约定 | M2 使用类型组织；M3 选表达契约 |
| M2 知识组织 | 稳定身份、认知粒度、知识组合、目录与视角 | 独立知识、关联、项目边界 | 项目知识空间、任务/功能的阅读投影 | M5 连接跨层；M4 管理修订 |
| M3 知识表达 | Content Contract、表达轮廓、阅读视角、渐进披露 | 目标问题、事实、内容类型 | 可读且可检查的业务与技术成果 | M8 评价真实性与可用性 |
| M4 知识治理 | 权威事实、提案、核验、批准、发布、基线 | 人/AI候选、证据、决策责任 | 可引用的规范版本、审计及冲突 | M6 决定变更包；M7 受批准事实约束 |
| M5 语义追溯 | 明确关系、双向追溯、字段业务含义映射 | 需求、规则、行为、实现、测试与来源 | 有语义的影响路径与实现映射 | 为 M6、M7 提供可调查依据 |
| M6 变更影响分析 | 变更语义、传播、闭合、需保持 | 变更意图、基线、代码/文档证据 | 影响处置、保留约束、验收计划 | M4 批准变更；M7 使用影响合同 |
| M7 AI 认知治理 | 任务认知上下文、角色授权、漂移防护、回写 | 任务、权限、基线、工具证据 | 候选成果、评审差异、交付知识 | 调用其余机制，不自行定义第二套事实 |
| M8 认知质量 | 正确、充分、可判定、可读、可追溯、完整性 | 事实、表达、行为与用户认知任务 | 缺口与验收结果；错误模式防再犯 | 反馈到所有机制而不是以数量打分 |

### 三个相互配合的产品体系

知识体系（M1/M2/M3/M5）决定「知道什么、怎样解释」，治理体系（M4/M6/M8）决定「为什么可信、怎样修订、何时完成」，认知服务体系（M7 串联其他机制）决定「怎样为人和 Agent 提供可用结果」。每个机制的行为和边界在对应文件展开。

## 4. 用户、工作与项目生命周期

产品负责人/BA/领域专家审核目标和业务语义；架构/技术负责人审核职责、约束和技术设计；开发人员从已有知识获取目标行为、实现约束、影响和验收；测试从业务判断构造独立案例、核对实现；售前售后在授权下获得准确解释；外部 Agent 读取上下文、提交证据和提案；知识负责人治理身份、冲突与版本。一个人可以担任多个职责，小团队无需为了审批增加岗位；关键高风险决策不能由未经授权的 Agent 自批。

三类工作：认识项目（项目及业务/技术全貌）；建构知识（接入与整理、核验与发布）；使项目演进（需求→调查→决策→开发→测试→知识回写）。项目创建时允许完全空白，没有内容比假数据更诚实。老项目先承认事实缺失；新项目从目标规范和设计开始，产生实现观察后持续对账。

## 5. 产品范围与非目标（R）

必须有：多项目隔离、项目介绍、标准认知框架与领域词汇、知识阅读/编写/引用、导入及冲突、检索/助手、证据、适用性、版本/审核发布、反馈/问题、Task 认知与影响、验收、Agent 入口、知识回写、权限与审计。正式产品要求真实持久化、多人协作、安全与可运维（工程 V1.2）；本稿只确定产品语义，不指定数据库、UI 技术或生产选型。

不是：通用知识图谱编辑器、画图软件、替代 Git/IDE/CI/Azure Boards 的工程执行系统、对所有源码万能自动逆向的承诺、替代业务专家的审批者、任意项目数据的中央无限复制仓。可以连接这些工具，知识资产仍由本项目治理。MCP/API/Skill 是承载方式不是产品菜单。原型要做减法，正式产品也不应在没有认知价值证据时扩展绘图；是否未来可选图表见 DEC-07。

## 6. 衡量成功

采用真实工作任务衡量而不是知识数量：陌生开发读完后能预测业务正反例；业务负责人能基于输出评审而不用手工填模型；Agent 能正确区分约束与变更，并提交有证据的闭合报告；同一事实在多处解释一致；未确认或冲突的事实不会冒充权威；代码、测试、部署与知识版本可核对。具体对照实验与阻断标准见 11。
