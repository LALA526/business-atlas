# 14｜交给下一个 Agent 的统一设计交接与知识维护规范

状态 R。本文件可直接给接手设计/工程的 Agent。不是要求它重做所有研究，也不是把产品设计资料再变成新的长提示词。它规定如何用本包和原基线开展后续工作、如何持续维护本产品自己的知识资产。

## 1. 交接输入及阅读方式

输入：本包 README 与 01–14 文档、V1.2 原工程包及旧需求追溯、现有原型及已知缺陷（若需实际修改原型）、获授权的真实业务资料。先读 README、01、12/13，获取目标、决定与冲突；只在当前任务涉及相应机制时读对应的 02–11。不要把所有原型 HTML、历史文档与测试日志复制进模型上下文。需要事实时按来源查证、使用稳定引用，记录已读版本。项目事实缺失时主动调查而不臆造。

正式开始前检查：本任务目标与已批准范围、用户明确意图、关键不变量、相关领域语义、历史设计决定、知识基线/代码版本、可用工具与权限、验收与知识交付。对产品范围存在冲突（如旧 VIS）时建立明确的决策/变更记录，而非自行静默覆盖。

## 2. 作为项目负责人的工作立场

你不是接单写补丁的外包者。你要在现有授权内对整个项目长期结果负责，理解用户意图，主动调查它在所有适用层次的影响，发现冗余、遗漏和无效假设。在普通工程选择上独立判断、给出推荐与理由；必要时反驳不正确的初始方向。用户的意见是认知入口，不是定义所有影响面的清单。

不能为了少写代码、少读文件、少运行检查而改变既有业务规则、接口语义或职责归属。不能用用户最新一句话覆盖所有批准知识。遇到需要业务确认的关键语义，先用证据分析和推荐降低人的决策负担，明确哪项决定需要批准；不在每个内部细节停下来问用户。

最终完整产品范围不以 MVP、第一阶段、一次原型演示、架构和分模块成果代替。执行可以按依赖并行；Leader 确定共享约束和设计，开发 Agent 按合同实现，独立验证 Agent 审查并从业务规范判定结果。产品自身的 Agent 认知服务不等于其开发任务编排系统。避免新增与目标无关的平台/引擎。

## 3. 不同团队的交付合同

| 角色/工作 | 必须产出 | 完成证据 |
|---|---|---|
| 产品/BA | 业务目标、术语、规则、案例、未决/推荐、语义差异 | 表达契约与业务审批，读者能判断样本 |
| 架构 Leader | 基于批准规范的职责、共享接口、约束、影响及决策 | ADR、合同及风险证据，不擅改业务 |
| 技术设计 | 全链数据/控制语义、调用者、更改/保持/迁移、预期验收 | 完整影响调查、跨层映射、独立评审 |
| 开发 Agent | 实际实现、分支/PR、相关测试、知识候选、影响完成情况 | 实际 diff、测试运行、未验证事项和 PR 引用 |
| 独立验证 Agent/QA | 从规范及旧行为独立核验目标、回归、边界、权限和闭合 | 通过/失败/未知及证据，反向检查旧路径 |
| 集成/发布负责人 | 合并后 Manifest、部署、配置/迁移与恢复、知识与部署对账 | 真实提交/构建/运行证据，版本一致与债务记录 |
| 知识负责人 | 领域身份、来源、候选修订/冲突、审批与基线发布 | 归属、版本、决策、历史可追溯，非手填所有关系 |

详细工程任务、分支/工作树、恢复、预算与依赖按原 V1.2；本稿只给产品/知识治理约束。真实生产设计与实现必须具备必要专业评审，不以原型模拟安全和并发能力代替。

## 4. 设计研究或变更应如何留存文本

每次新的产品研究不是新增一份全量历史报告，而是更新现有权威文档中相关段落，并登记变更：

- 新概念或语义：02 或 03，对既有类别、关系和规范的区别；说明为何需要新的独立身份。
- 内容表达或呈现：04、08，写出具体人类阅读成果、错误示例和验收；不默认新增页面。
- 治理及影响：05、06，写明参与者、输入、状态/行为、权限、证据、失败和恢复。
- AI 服务及使用方式：07，写清目的、输入/输出、限制和失败处置，不靠抽象使命。
- 场景、案例、验收：09–11；所有值注明真实、用户报告、推断或合成；测试预期不能当结果。
- 重要决定、未解决问题、风险：12，以稳定 ID 保存候选、证据、推荐、批准人及生效版本；13 记录与旧基线冲突及替代范围。

一份知识只有一个权威维护位置；其它文档引用编号和路径，报告/Word/Excel可生成阅读视图，不独立维护事实。每次变更提供旧/新、原因、已调查影响、需人决定事项、实际证据和后续核验。人可以仅审阅本次变更差异，而不是每次重读整个包。

## 5. 本次包如何成为 Self Project 初始知识

创建项目 `Business Atlas`；导入本包文本为来源候选，按 01–07 识别产品原则、领域词汇、需求、规则、设计约束、参考与关系。PD-ID 与 DEC-ID 可作为外部稳定身份映射。U 标记记录用户明确表达的方向，R 为本次推荐，X 为缺证据；不自动把本包所有文字批准。第10份演练的 EX 项只能放在标注为示例的测试/演示上下文，不能污染 CPQ 项目或冒充真实实现。获得实际审批后将适用知识发布为第一个 P1.0 权威基线。后续真实开发按 V1.2 Git 知识候选及 Manifest 回写；已有文档直接作为可定位来源，不重复产生一套内容。若同一个工程需求在旧基线和本稿有差异，先走变更审批。

## 6. 研究设计交付的完成标准（当前包）

当前产品设计已包含：明确产品哲学及八套机制；知识本体词典及领域语言；语义组织/追溯；表达和认知质量；审批版本/权限；影响调查与变更闭合；AI 认知服务和使用合同；页面/旅程；黄金案例、要求与验收；设计决策、开放问题与历史需求映射。它可以成为后续产品审核和正式工程设计的输入；它不宣称原型已更新、真实业务事实已批准、模型已通过实测、生产代码已经完成。

**负责人审阅重点**见 12 最后部分。批准明确产品范围及核心约束后，提交受控产品修订给正式开发 Leader；通过真实工作任务验证并持续维护，而非无限循环修改原型。项目完成最终必须有真实交付证据支持所有确定范围，并让 Business Atlas 自身知识与实际实现同步。
