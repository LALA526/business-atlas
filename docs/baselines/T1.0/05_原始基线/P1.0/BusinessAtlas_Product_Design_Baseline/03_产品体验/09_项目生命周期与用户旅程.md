# 09｜项目生命周期与真实工作旅程

状态 R。各旅程均以人的轻量入口和实际产物为中心，底层机制及服务负责全部可自动承担的复杂工作。定义跨模块验收，不是开发进度阶段。

## J1 接管老项目：从未知到可信认知

| 环节 | 谁负责 | 工作与产物 | 人的注意力 |
|---|---|---|---|
| 建立项目边界 | 人 + AI | 项目定位、范围、角色与资料来源 | 确认目的和访问授权 |
| 收集及整理 | 外部 Agent | 从源码/文档/专家经验提取术语、对象、规范声称、观察、关系和问题；形成 AKP 或等价提案 | 只补充缺失权限/无法独立获知的业务事实 |
| 接入 | 系统 | 校验包、版本/外部身份、冲突、范围，差异预览，原子落草稿 | 审查冲突，不录入每个对象 |
| 核验与重构 | Agent + BA | 根据表达契约整理项目概览、功能规则、案例、实现映射和未知 | 审阅可读业务成果，确认目标规范 |
| 发布 | 系统 + Owner | 完成必要审批、基线发布、生成知识阅读及可用上下文 | 批准明确范围 |
| 继续完善 | 全员 | 新资料提案、问题闭环、历史与冲突追踪 | 基于问题进行必要评审 |

边界：无法连接真实资料时只提供模板/候选，不宣称已完成反向认知。源码可显示当前行为，不能自动说明原本业务目标；如果专家确认现状就是规范，建立独立决议并绑定证据。

## J2 从零创建新项目：规范先于实现

人给业务目标或原型想法。Agent 建议领域词汇、范围、能力、目标需求和规则，系统支持按功能展示需求/规则/设计。BA 与用户评审，重要决策落入明确批准基线；架构/技术 Agent 基于规则进行职责及接口选择，独立评审，形成设计知识。实现 Agent 取得版本化 Task Context，代码/测试与知识候选同行；观察、符合性、部署随后对账。项目即便没有代码也能管理目标知识，不能假造实际运行事实。原型仅是需求解释，实际设计变化须正式评审。

## J3 人阅读陌生功能

人打开项目首页，从业务能力或者搜索进入功能，无需知道内部 ID。首先看到目标、核心判断、结果、关键未知；可直接用一个新案例判断预期。若只想了解业务，不必阅读接口签名；若需要修改，可深入到术语/字段、现有实现、源与版本。发现描述不清在相关段落提出问题，形成可定位 Issue；AI 调查并提交修订，审批后原页面可读到新结论。验收：新成员能正确解释目标、决策及异常，并指出哪些仍未知；不得把候选当正式结论。

## J4 基于既有项目提交新需求

使用者只写需求意图，例如“新增一项条件以避免参数重复应用”。AI 读取发布规则与实际观察，区分新旧行为、保持项和证据缺口，形成候选目标并调查完整影响面。将高风险业务选择、推荐与依据组织为可审核成果；用户只评审业务需求/规则/设计及关键影响。审批后形成清晰 Task Context；根据变更传播建立相互依赖的开发/测试工作项。开发后独立验收、知识修订、发布及部署对账。没有真实调查证据时显示候选/无法确认，不可跳过待解决的必要决定。详见 06、10。

## J5 技术重构而不改变业务

人或 Agent 发现重复参数/无效兼容，或想优化查询。平台提供已批准规则、边界、职责以及实际实现版本；Agent 以行为等价为约束进行完整调用链调查，比较数据语义、权限、失败、分页/排序等并给出收敛方案。如果属于已授权可逆内部技术决策，直接记录实施，不需要用户决定每个方法名。共享职责、关键接口或数据变化按技术/安全权限机制审批；任何业务语义改变都需业务决定。验收用新旧等价案例和原行为回归，提交实现及知识更新。若发现原规则错误，单独形成业务变更，不以重构名义更改。

## J6 售前、售后与领域问答

用户在项目助手问“这个系统是否支持某种配置？”。系统读取授权、批准范围和观察；AI 给明确支持/不支持/待确定及适用条件，可引用业务解释与来源。 不用内部标识作为答案。客户敏感实现不外露。未知形成具体问题并交有权人员核验；回答修订后进入相同资产，下次可引用新基线。已部署系统行为与批准目标不一致时，必须指明版本差异，不能对客户承诺还未实现的能力。

## J7 人审 AI 成果的反复对齐

提交 → 人就具体段落或规则行给意见 → AI 复核认知基线与相关影响 → 形成修改差异、推荐和保留项 → 重新提交 → 对有效修订批准 → 发布。用户不需要维护关系，系统自动记录每次意见、决定、版本和来源。若新意见改变已批准业务规则，必须明确标识变更而非直接编辑历史；评论标已解决需要关联处理证据。不同审批人使用同一候选修订；候选被改动后实质变更重新批准。不能只保存一个长聊天记录作为治理成果。

## J8 开发即知识交付 / Self Project

Business Atlas 自身是被它管理的一个项目（独立 `Business Atlas` 项目身份）。当前文本包可作为首批候选资料：产品理念、领域术语、业务规则（例如批准与发布分离）、功能及设计约束、决策和验收。产品文档与真实实现观察必须标记不同事实性质。

正式开发每次 PR 提交所属任务、影响、规则/实现/ADR 变更、来源定位和验证候选；CI 合并后生成真实 Manifest。系统未上线前使用工程 V1.2 的 Git 知识账本自举，平台建成后受控导入、核验和发布，用相同治理机制维护自己的知识。不能仅将 HTML 中的演示记录冒充 Self Project 真实执行。最终人在本产品内可读到本项目真正的需求、规则、设计、实现、决策、版本和约束；下一次开发能引用已经确认的知识。业务项目（CPQ）验证复杂领域认知，Self Project 验证工程知识闭环，两者缺一不可。

## J9 权限、并发与异常旅程

同一规则被两个 Agent 从 B1 提交候选，先发布者形成 B2，另一个收到冲突/过期提示；系统生成差异和需要再审的范围，不丢历史或默默覆盖。撤销阅读权限后用户不能通过旧缓存、Agent契约、历史、导出绕过；仅有阅读权限的主体不能创建/审批任务。来源失效则重验相关结论。代码部署回滚后保留目标规范、更新实际观察并显示差异。工具失败时保存有效调查和任务状态，恢复时基于基线差异继续。

## 最终完整产品的价值闭环

项目认识 → 已确认知识 → AI 根据知识处理需求 → 形成可审成果 → 人评审 → 实施与验证 → 知识回写 → 新版本继续认识与开发。任一旅程断开都影响完整产品价值。各项可按真实依赖开发，但正式完整交付须覆盖所有适用旅程及 V1.2 原要求的最终确认范围。
