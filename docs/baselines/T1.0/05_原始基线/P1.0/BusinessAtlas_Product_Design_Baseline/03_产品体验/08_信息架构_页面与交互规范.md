# 08｜产品信息架构、页面形态与轻量审核交互

状态 R。此处给出可作为原型/产品设计依据的界面规范及内容样板，不要求开发 HTML，不新造绘图系统。保留既有原型的项目工作区和六入口方向；重做内容组织方式而非全部推倒。

## 1. 默认信息架构

| 一级工作区 | 用户来这里做什么 | 默认呈现 | 按需深入 |
|---|---|---|---|
| 项目概览 | 迅速理解这个项目 | 一句话定位、背景/边界、核心业务能力和系统、关键术语、重要待审成果 | 领域、技术、运行及治理全貌 |
| 知识目录 | 查询或维护某类知识 | 固定五维骨架，搜索、类型、业务领域 | 可选类型、缺失状态、身份/修订、领域扩展 |
| 业务与系统 | 阅读功能、场景、规则、实现 | 按功能/能力或系统为主轴；人可读知识页 | 规则详情、属性定义、上下游、来源/历史 |
| 变更与审核 | 审阅 AI/人提交的成果 | 待我审核队列、变更目的/差异、关键决定 | 影响、完整 ChangeSet、决议、证据、历史 |
| 任务与问题 | 提出需求、处理问题、观察进展 | 简洁需求入口、Task 目标/当前结论/下一步 | 实际调查、审批/交付、Agent记录 |
| 交付与验收 | 判断变更是否完整完成 | 目标行为、保持约束、验收结论和缺口 | 代码/测试/知识基线/部署对账、导出 |

项目切换及管理放在工作区顶部；导入资料是项目菜单中的低频动作，不占一级导航。项目助手采用固定角落轻量入口（当前偏好右下角），在任何阅读位置打开时默认绑定项目、知识与当前修订；提问、反馈、授权确认统一使用上下文浮层，而非独立大工作台。待审成果在首页可直接进入，用户不必了解目录结构才能协作。实际位置、移动适配由原型验证，不再引入多级独立管理中心。

## 2. 页面 A：功能阅读与编写单元

**默认样式：** main 内容面板顶部显示功能名称、业务目的、事实层级与必要状态；核心 Tab 为业务需求、业务规则、业务设计。Tab 内容是组合后的可读文本，不按底层对象数量逐张卡片排列。功能有已批准和候选版本时，默认正式阅读，可切换候选差异。读者不需要输入内部 ID。不重复同一句摘要。

| 位置 | 内容 | 交互 |
|---|---|---|
| 顶部 | 功能名、简短目的、适用范围、重大冲突提示 | 查看上下文、来源/版本、发起反馈 |
| 业务需求 | 问题、目标、使用者、业务范围、成功结果 | 点引用或段落打开关联知识 |
| 业务规则（默认推荐） | 情境、判断、结果的短文/条件表、关键异常、例子 | 看正反例；按需展开规则引用和完整条件 |
| 业务设计 | 已批准设计、实际观察、未实现差异、实现映射及职责 | 明确三个小标题；点组件/接口/字段深入 |
| 可选内容 | 业务参与者、对象语义、流程/状态、数据、验收、运行约束 | “更多内容”根据适用类型与认知任务启用；不是填写要求全集 |

**默认业务规则页样板（演示，不是已批准 CPQ 事实）**

> 应用非标参数：仅允许将参数应用到业务判断认定的对应配置。是否相同，必须按照以下已确认的业务属性组合判断。
>
> | 业务情况 | 判断依据 | 处理结果 |
> |---|---|---|
> | 参数有名称 | 具体比较字段尚待确认 | 不能判断是否可应用 |
> | 参数无名称 | 无名称分支比较口径尚待核实 | 不能根据现有资料自行补造 |
>
> 待确认：名称为空字符串是否等于名称不存在？哪些字段构成业务匹配键？
>
> 看业务案例 · 看当前实现 · 查看来源及版本

这比将 `Rule`、`Action`、`Assertion`、`DataEntity` 的列表逐个排列更接近用户真正关心的问题。具有完整规则时，表格必须展示真实条件和具体结果；不能用缺失模板生成“根据规则处理”之类空话。

### 编辑与 AI 写入

人可以写一段自然语言、粘贴资料或指出一条规则修改，AI 组织为对应 Tab 的候选成果；可手工修订，不需要输入每个谓词。编辑区同阅读结构。选中一段话可“提出修正意见”；内容检查就地提示“缺少比较依据”“混入实现”“与现行规则冲突”，而不是展开几十个必填字段。底层自动记录知识身份、版本和引用。若业务依据不足，保存待澄清草稿而非完整合同；经验写作者可直接维护结构化细节。

## 3. 页面 B：领域语言与知识详情

搜索业务名词进入术语页：定义、所属语境、业务含义、示例和反例、使用在哪些规则/对象、映射到哪些字段或技术对象、来源及状态。别名可查同一概念；同名不同义显示语境供选择。业务规则可独立阅读和评审，在多个功能中引用同一规则修订。技术字段详情从物理信息转到业务属性及使用它的判断，不以技术名称定义业务语言。

对于场景复杂流程：优先用连续阶段的文字表达，每阶段说明触发/参与者、关键判断、结果/下一步和异常回退；对条件分支使用表格。不能把归属或依赖误当执行顺序。对技术组件：优先职责、提供/消费契约、数据与错误、设计约束和来源，不必显示业务需求三 Tab。当前版本不画自动流程、状态、关系或架构图；原始外部图可作为有权查看的资料，保留语义和证据，不再开发渲染/布局引擎。

## 4. 页面 C：审核 AI 成果（核心工作入口）

这是产品最应打磨的交互。用户在评审中不应维护底层模型。

**队列条目**只显示主题、业务影响摘要、提交者/Agent、需要哪类决策、提交时间和阻断风险。筛选“待我审核”“需补证”“已批准待发布”。不显示平台内部流水线所有状态。

**详情**：

| 区域 | 示例内容 |
|---|---|
| 本次决定 | 将某业务动作的匹配条件改为新规则；原业务目标不变 |
| 候选成果 | 需求、规则、设计、实际行为以简洁 Tab 呈现；默认聚焦改变的规则行 |
| 前后对比 | 原条件/结果与候选条件/结果；明确不改变的关键分支 |
| 影响与判断 | 已调查的真实影响；仍需决策的高风险未知；关键证据可展开 |
| 意见与操作 | 行内评论、要求修改、批准明确范围、拒绝；权限不足提示相应 Owner |

人说“第二行不对，名称为空时应当走另一分支”，系统锚定该规则修订和意见，Agent 接受后分析对其他规则和同一术语的影响，提交可对照差异。不得用这条意见重新改写所有原本已批准的内容。如果意见与其他已批准规则冲突，给出冲突及推荐，提交新的明确变更决定，不直接修改基线。

批准前显示具体要批准的范围及必要保留项，不全选不相关知识；可批准独立条目，但存在相互依赖时必须作为同一决议组。已批准内容由系统依条件发布；读者看到更新后的实际知识成果。需要区分“已批准待发布”和“已发布”，不是分享一个 AI 聊天答案。

## 5. 页面 D：提出需求与 Task 进展

轻入口：一个需求/问题描述框，可选关联功能、资料和版本。无默认生成的泛泛需求，不要求填写全套调查表。AI/系统根据实际资料组织成果，缺资料时形成待澄清，不阻断无关任务。

| 默认阅读块 | 内容 |
|---|---|
| 想改变什么 | 原意、当前行为、目标变化及重要保持约束 |
| 已确认结论 | 已确认需求/规则/设计、实际调查中关键结论 |
| 需要关注 | 业务歧义、冲突、必须批准事项、重要未知 |
| 下一步与交付 | 正在调查/待决策/可实施/待验收及证据状态 |

下层可展开影响候选、调查过程、关联任务/代码、测试、知识提案/发布、详细日志。若未连接真实代码 Agent，界面显示“仅基于当前知识形成候选”“尚未调查仓库”，不能出现自动调查完成的假象。状态来源于实际记录和授权操作，不可被用户任意切换为完整完成。

## 6. 页面 E：交付、助手与反馈

交付验收默认展示本次目标与保持项、实际验证结果、阻断/债务、发布/部署版本状态。可从问题结论回到规则、业务案例、实际代码证据。代码完成、知识批准、知识发布、部署和最终验收分别显示。项目助手在当前上下文中给人答案与引用；无法确定时说明原因并支持生成 Issue 或候选修订，不直接覆盖未批准事实。售前可查授权业务范围，不显示敏感实现。

## 7. 页面评审标准及减法

1. 每个默认内容区都有独立信息价值；禁止同一说明在摘要、条件列、判断列重复。
2. 重大冲突与未知在相关结论旁出现，不能为了简洁埋在底部。
3. 用户能从功能/业务名词找到目标内容而无需 ID，多层跳转能返回原位置。
4. 功能阅读优先文字和必要表格；结构/关系/日志/原始数据默认折叠。不从表单要求推导复杂布局。
5. 原型保留少量代表性场景和高价值验证；不要内联所有历史知识/测试/旧实现。保留旧数据兼容及关键权限/历史/语义/审批闭环。原型减少复杂性不等同正式产品减少必要质量要求。
6. UI 的具体视觉风格可以在现有原型基础上改良；先验证内容和操作，不增加新的一级菜单。用户能否正确理解、审核并用它完成工作，是验收标准，不是有多少功能页。
