## 2. 产品验收分层

**语义验收**：领域概念、条件、规则、关系、上下文、版本、权限；通过结构检查、规则求值（可确定时）、负例和源事实比对。**表达验收**：实际读者能否理解与判断；不依赖批量测试字符串出现。**治理验收**：从真实输入到候选、回评、批准、发布、变更、回写的成功和失败路径；不能只验证 pending 标签。**工程验收**：正式系统真实 API、权限、并发、持久化、真实 Agent、CI/部署/恢复；沿用 V1.2，按确认范围验收。

| 验收标识 | 核验任务 | 成功标准 / 阻断条件 |
|---|---|---|
| AT-P01 | 读者理解参数规则 | 给定 A 的规则与陌生输入，正确判断全部关键正反、模糊/缺失、重复案例；不能靠看答案或源码 |
| AT-P02 | 识别需求/规则/实现分层 | B 的实际行为不等于目标，能说明候选语义差异及决策缺口 |

## 3. 真正验证质量：真实试点设计（未执行）

目的不是证明某页面存在，而是验证平台是否帮助人和 AI 形成更准确、低成本、可持续使用的认知。取获授权的真实 CPQ 功能和变更，先由熟悉项目人员建立独立参考答案（业务规则、正反例、已知未知、真实调用链及潜在风险），不能让被验证的 Agent 自己生成标准答案。Self Project 另用真实开发仓库和 PR 验证回写。

建议对照两组工作条件：A 原有源码、文档和聊天工具；B 相同资料权限 + Business Atlas 的批准知识与任务上下文。给处于类似经验水平的陌生开发者/不同 Agent 同等任务；避免先做 A 再做同题 B 的学习效应，采用不同但等价任务交叉安排。记录模型版本、预算、输入来源、项目状态、规则和独立评审标准。建议初始小规模试点（例如 3–5 名参与者、每类多次任务）作为发现问题，不宣称统计显著；规模由真实可用资源决定。

观测指标：关键业务判断正确数/应判断数、错误肯定数、重大遗漏数、缺口是否具体、找到依据的比例、额外提问次数和人工整理时间、真正需要人决策的次数、无谓界面操作/手工维护、变更影响真实召回（参考集合与已确认范围）、误报和未查覆盖、交付知识版本对账、模型上下文成本。对风险分层，不把不适用项计入分母。设立建议门槛：关键已确认规则不得错误、关键未知不得被伪造、越权与历史篡改为零容忍、关键影响无遗漏才通过对应样本；速度/成本目标记录实测基线后确定，不虚构“30秒一定读懂”或提升百分比。

## 4. 当前原型与最终产品的区别

原型要证明内容形态、基本知识语义、轻量审阅链路和主要状态转换；采用少量高价值 smoke/语义负例（导入、阅读、审批、Task闭环、权限历史、符合性）。不要为每次 UI 迭代无限累积测试和生成巨大演示数据。正式系统的生产安全、数据一致性、真实并发、备份、权限、集成与质量门槛不因此缩减。原型删掉绘图能力后保留 Flow、State、Rule 和所有语义；旧图形专项测试可转化为文本语义守恒，不能直接把缺陷覆盖删掉。

## 5. 完整产品完成定义

完整最终产品全部确定范围（经 13 的旧需求衔接和产品审阅确认）实现；提供真实代码、部署、运行与回滚、必要测试证据、可使用的产品认知服务、知识资产以及用户可审的说明。每条需求由版本化的实现/测试/知识/交付证据支持。架构设计、候选知识、模拟审批、单条纵切或测试报告单独不构成产品完成。待明确高风险产品决定不得静默跳过；未实施或待验证的内容如实列为未完成。任务可按共享约束及依赖并行实现，不降低最终目标范围。
