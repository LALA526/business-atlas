# 10｜业务黄金样本、反向验证与变更推演

状态：演练设计已形成（R），实际用户或真实项目验证未开展（X）。样本用于检验本稿的通用语义与呈现，而非给公司 CPQ 发明业务规则。以下 EX-* 对象均为**合成的演练知识**，其示例中的“已批准 B1”仅指测试前置条件；没有真实人类审批、代码运行或部署事实。真实 CPQ 中的参数判断字段、完整查询行为及数据语义未提供；用户报告和实际源码/运行观察分别标记。

## A｜参数应用：一项功能完整认知说明

### A.1 已知现实输入与待确认边界

用户曾说明：有 parameterName 和没有 parameterName 应走不同匹配分支，比较相关业务字段；一致则应用、不一致不应用；“无参非标描述不会重复”是某判断前提。实际字段组合、大小写、空值、唯一性数据约束、异常及行是否处于同一个业务范围仍需真实资料核验。禁止把以下演练中的字段组合当成实际规则。这一事实缺口本身应能进入平台作为待确认知识。

### A.2 合成项目 EX-CPQ：功能页中的三 Tab

**业务需求 EX-REQ-01@1**：将导入的非标参数准确应用到目标产品配置，不能错误应用到其他配置或存在歧义的重复参数。受益者为配置工程师；成功条件是每条具有唯一合法匹配的参数才应用，匹配不到不更新，歧义或缺关键数据须明确处理。此处不要求具体 SQL 或表结构。

**领域词汇（独立知识单元）**：

| ID | 属性 | 演练定义 |
|---|---|---|
| EX-ATTR-01 | 配置标识 configurationKey | 目标配置的业务身份，不同标识绝不相互匹配 |
| EX-ATTR-02 | 参数路径 parameterPath | 配置中参数所在位置的键，不能为空 |
| EX-ATTR-03 | 参数名称 parameterName | 可选业务属性；明确给定 null 或空字符串表示无名称；缺少该事实表示未知，不等于空值。为演练简化：不做 trim，实际非空字符串区分大小写 |
| EX-ATTR-04 | 参数描述 description | 无名称分支的匹配依据之一，精确比较；为空/null 表示数据无效；缺失表示未知 |
| EX-CON-01 | 一致 | 配置、路径相同，且按名称存在性选择的业务键等价；不能混合比较有名称与无名称对象 |
| EX-CON-02 | 重复 | 同一匹配键下存在两条及以上候选，即使值相同也属于歧义 |

**业务规则**（模拟批准基线 EX-B1）：

| 规则 ID | 情境与前提 | 判断依据 | 结果 |
|---|---|---|---|
| EX-RULE-01@1（范围与有效性） | 任一匹配请求 | 配置标识和路径有效且一致。名称事实存在；若名称无值，描述有效且已知 | 不同配置/路径不匹配；必要输入确定非法则拒绝并提示数据错误；未知则待核验，不写数据 |
| EX-RULE-02@1（匹配键） | 通过前置条件 | 有名称：匹配同配置、同路径、有名称且名称精确相等的目标；无名称：匹配同配置、同路径、无名称且描述精确相等的目标 | 得到候选集合，不把候选当最终应用 |
| EX-RULE-03@1（唯一性与处理） | 已取得完整候选集合 | 候选数为0、1或大于1；候选关键字段不可判定且可能影响唯一性时先待核验 | 0→不应用；1→应用到唯一目标并保存审计；>1→拒绝应用、报告重复冲突；不完整→不写入，待核验 |
| EX-INV-01@1（不变量） | 所有分支 | 本次请求不能更新其他配置、歧义目标或未经确认输入 | 保持该约束与审计，不允许技术改造破坏 |

优先顺序：有效性与范围门槛 → 匹配键 → 唯一性判断 → 应用。异常/默认明确：无命中不应用；缺必要事实不能猜为“条件不成立”或默认成功。这些规则构成一个业务决策链，而不是函数调用链。

**业务设计 EX-DES-01@1（演练方案）**：配置操作负责提交参数与配置身份，匹配服务负责按批准规则确定候选并返回结果，应用操作只在唯一合法结果时更新并记录审计。物理技术字段映射：`ConfigKey`→EX-ATTR-01，`Path`→02，`Name`→03，`Desc`→04；设计应遵循 EX-INV-01，不允许前端或接口适配器为少改代码自行另定义匹配语义。事务、并发和实际表结构尚无真实实现。本案例只把设计当预期方案。

### A.4 语义组织关系（以逻辑关系为例）

EX-RULE-01/02/03 `refines` EX-REQ-01；EX-RULE-02 `usesFact` EX-ATTR-01/02/03/04；EX-RULE-03 `usesFact` EX-CON-02；EX-INV-01 `constrains` 参数应用动作；动作 `satisfies` EX-REQ-01；EX-DES-01 `implements` 规则/动作（设计目标，非实际实现证据）；每条 EX-A* `validates` 对应规则版本；字段映射、关系、案例均有独立语义，不靠名称模糊匹配。

## C｜字段删除：从抽象需求追踪多条规则

以 A 的合成项目 EX-B1 为前置，假设开发请求「为简化数据结构，删除存储字段 `Name`」。不假设用户已经批准删除 EX-ATTR-03 的领域语义。

### C.1 影响分析成果（示例证据与处置）

| 影响对象 / 路径 | 本案例中的证据 | 判定与处置 |
|---|---|---|
| `Name` → EX-ATTR-03 | A.2 的映射 | required：需要替代映射或领域变更；不允许简单丢名称 |
| EX-ATTR-03 ← EX-RULE-01 | 门槛要求名称事实已知 | required 复核数据缺失语义；保留区分未知与无名称 |
| EX-ATTR-03 ← EX-RULE-02 | 两个分支依赖名称存在以及名称值 | required：若无等价事实，新旧行为不同，不能删除规则分支 |
| EX-ATTR-03 ← EX-CON-02 ← EX-RULE-03 | 匹配键定义决定重复/唯一 | required：字段消失可能合并两个不同名称，产生歧义或错误应用 |
| EX-RULE-01/02/03 → EX-REQ-01 | 规则共同细化需求 | preserve：正确应用目标与 EX-INV-01；不能以删除字段为由改变需求 |
| EX-DES-01 / 操作调用者 | 演练设计仅确定职责，无真实代码 | potential/unknown：调查请求、存储、前端、审计、旧分支、接口及配置；不可宣称无影响 |
| EX-A01/03/05/07/10 等 | 具体案例引用规则 | required revalidate：覆盖名称存在、无名称、重复与缺失 |
| 部署与迁移 | 实际存储与数据未提供 | unknown：检查历史数据可逆迁移、兼容窗口、发布与失败恢复；关键未知未决不交付 |

### C.2 可观察的业务反例（为什么不能仅去掉字段）

C1/P1 同时有名称 N1、N2，描述均 D1 的两条记录。按 EX-B1，名称 N1 的请求能唯一匹配 N1；如果把所有记录都变成无名称并只比较描述，就得到两个相同匹配键，原有结果从应用变成重复冲突，甚至在错误实现中可能取第一条。EX-REQ-01 及规则 02/03 被破坏。字段删除不能只看编译通过或被多少代码引用。

### C.3 方案与推荐

方案甲：保留业务属性语义，通过新的等价载体提供原名称/存在性事实；只修订映射和实现设计。优点是不改变规则，需证明数据和接口迁移等价。方案乙：删除业务名称概念，统一新键。需要业务 Owner 批准新的匹配及重复语义，原目标仍需验证，并规划数据迁移与兼容。方案丙：暂不删除；如果暂无可证明等价方案而无业务授权，这是安全的暂定处置。

推荐甲，前提是实证有等价载体且全链路保持；否则宁可暂缓，不为技术简化擅改业务。如果真实改动只改名/搬迁，也不能自动视为已等价。由于没有真实源码，此处不能确定具体 API/迁移方案，保留必要调查项。

### C.4 批准与闭合演练

合成批准选择甲（仅作为假设测试前置）：EX-B2 发布新映射修订、设计修订和相关验收复核要求。EX-RULE-01/02/03@1 保持原规则身份和版本；不得因映射版本变化重写批准规则。旧 B1 仍可读。实现候选和测试待真实验证；仅设计获批时 Task 状态为可实施而非完整交付。演练输入若提供一套明确标记的模拟 PR/Manifest、满足 A 的所有案例、通过代码/知识对账且不存在阻断未知，预期允许模拟完成；缺任何必要证据则阻断。这不是实际部署。

## D｜技术冗余、范围与职责漂移的反例

用户曾指出 A UNION B ≡ B 时 Agent 应主动收敛；本例用集合 A={1,2}、B={1,2,3} 说明数学等价，前提 A⊆B 和集合语义一致。若实际 SQL `UNION` 去重，而单独 B 可能有重复行，那么直接替换 B 不必然与原结果等价；例如 B 为 [1,1,2]，集合去重结果不同于 SQL 直接返回重复。还需检查选择列、空值、排序分页、访问权限、错误及副作用，不能拿数学式当全部证明。Agent 应给出建议与核验路径，若确认等价则在授权范围内收敛旧路径、重复参数、无效兼容；不需要把明显冗余永久留着等待用户点名。若等价未证实，标未知并限制实施。

对新消息“为了少改代码，把校验放到前端”：若已批准约束要求服务端判定，Agent 必须识别职责冲突，推荐保持服务端权威校验，前端可做体验层提示（候选技术建议）。不能因最新一句话取消批准规则。若用户确实要改变职责，经过影响调查与架构/安全决策后形成新修订；权限约束不能被绕过。

取本产品自身的规范候选「知识批准与发布分离」「只读主体不可创建任务」「符合性绑定目标及观察修订」。这是真实设计意图，尚待本稿正式审核；以下是预期负向样本而非新的运行结果。

| 试验 | 前置 | 预期 |
|---|---|---|
| E1 候选修订 | 已批准 B1，Agent 提新规则 | 正式阅读仍读 B1，草稿可审；未授权 Agent 不可批 |

## 结论

这些样本能够用于设计讨论、原型内容展示、独立 Agent 约束试验和验收预期。它们不是产品已经验证可用的证据。下一个真实试点要以授权 CPQ 业务资料、专家确认的规则及实际代码/测试替换合成示例；缺少事实不应等待无限期，也不能用演示取代真实验证。
