# 04｜知识表达、内容契约与认知质量规范

机制 M3/M8。状态 R。目标不是让人填完表单，而是让人和 AI 输出的内容读得懂、能判断、能维护。一个框、三个 Tab 是交互表现；下面的内容契约规定哪些问题必须回答、哪些层次不能混淆、什么成果才可批准。

## 1. 内容的四种性质与三 Tab

| 默认工作区 | 承载信息 | 不该混入 |
|---|---|---|
| 业务需求 | 背景/问题、使用者、目标、范围、成功结果及来源 | 不必要的 SQL、类、索引选型；未确认的判断规则伪装成需求 |
| 业务规则 | 业务情境、判断依据与逻辑、正常/异常/默认的结果、必要的不变量、正反案例 | 单纯代码调用链；空泛描述“根据规则处理” |
| 业务设计 | 为满足已确认规则而做的职责、数据和接口设计；明确分区展示当前实际行为、已采用实现、候选方案及差异 | 当前行为直接作为目标规范；候选设计被叙述为现有实现 |

业务要求、规范规则、实际行为、技术机制在语义上必须有区分；UI 可以三 Tab，也可在复杂功能中将当前行为独立展开。一个需求通常由多条规则解释，规则可支撑多个需求；功能页是它们的组合视图。不同类型知识可以选择不同模板，不能强迫纯技术组件也填写三 Tab。

## 2. Content Contract（知识表达契约）

契约由类型、版本、认知目的、最小必要内容、按需项、禁止混入的信息、关系要求、证据及校验规则构成。不是固定字数或格式模板。写作者可先自然语言描述，AI 将内容映射到语义；用户直接审查整理结果。成熟的知识应逐项引用适用的批准事实；缺失的必需信息明确为未知、争议或不适用（须有理由）。仅填写一个字段不是内容质量证明。

| 知识类型/表达轮廓 | 最小必要内容（必需但允许显式未知） | 按需扩展 | 质量负例 |
|---|---|---|---|
| 项目介绍 | 为什么做、谁使用、范围、核心能力/系统、关键未知 | 业务价值、历史、环境 | 只有技术栈、无业务定位 |
| 领域术语/属性 | 定义、语境、例/反例、Owner/来源 | 单位、值域、别名、映射、约束 | 只保存字段名、同义词含义不清 |
| 业务需求 | 问题/目标、使用者/受益者、范围、可观察成功结果 | 非目标、价值、质量限制 | 写“改 SQL”而未说明需要什么结果 |
| 业务规则 | 适用情境、输入事实、判断依据及比较口径、结果、默认/异常、来源 | 冲突优先级、时间/角色、状态转移、补偿 | “一致则应用”未说比较什么 |
| 功能说明 | 一句话目的、核心判断/处理、关键结果、例子、规范与实现的区别 | 参与者、流程、状态、技术链接 | 只列十条关联 Rule 名称 |
| 场景/流程 | 起因、前提、执行顺序、分支与守卫、结束、异常/回退 | 角色、输入输出、时间限制 | 按关联关系或数据库顺序推断流程 |
| 状态/生命周期 | 对象、状态含义、事件/动作、合法转移与前提 | 禁止转移、补偿与终止、历史 | 只有枚举值没有含义和规则 |
| 数据定义 | 业务对象/属性、含义、单位/空值、值来源与约束 | 生命周期、逻辑关系、物理映射、读写方 | 将 NULL 自动解释成业务“不存在” |
| 设计/组件 | 目标规则、职责及不负责范围、输入输出、处理/数据、副作用、错误 | 依赖、事务、方案权衡、非功能/迁移 | 未经批准将职责转给其他组件 |
| 接口 | 业务动作、调用者、请求/响应语义、前置和错误 | 幂等、版本、数据范围、权限 | 仅签名与字段类型，无业务含义 |
| 观察行为 | 对象、版本、环境、输入/条件、输出/状态、观察办法、证据 | 覆盖范围、可重现步骤、限制 | 由代码猜测运行结果却标“实测” |
| 架构/业务决定 | 需要决定的事、已知约束、候选/推荐、理由、后果、责任人 | 取舍、回滚、适用范围、验证 | 只写“采用方案 A”无依据 |
| 验收案例 | 目标规范精确版本、输入与环境、预期、观察结果分开 | 正反边界、回归、测试方法 | 预期通过冒充执行通过 |
| 运维/安全/工程知识 | 对象、目标、操作/约束、前提、风险、来源 | 运行环境、恢复/异常、权限、质量指标 | 把示例凭据当实际或可公开数据 |
| 变更成果 | 本次目标、现状→目标差异、保持约束、确认/未知影响、证据、验收及知识修订 | 设计备选、任务/交付版本、债务 | 把关系候选清单当调查完成 |

必须记住：业务规则是对业务如何判断的描述。条件与比较内容是不同信息；若一个简单业务只需要一句完整规则，不强制拆三列。复杂规则可用有序决策表，多个条件并发时定义优先策略。不要按“第一行获胜”“最新规则优先”或输入缺失当作 false 等未确认的默认行为。未确认的自由文本条件可读，但不能冒充可执行表达式。

### 表达案例：剥离混合信息

不合格："为了优化非标描述搜索，使用 CONTAINS 查询参数并根据 Keyword 匹配记录，前端显示正确结果。"

拆分后的候选：

- 需求：允许业务人员输入部分已知内容查找相关描述。若“部分”是否必须支持子串没有明确依据，列为待定。
- 规则：需要明确比较双方（关键词与描述）、比较语义（精确/前缀/子串/词元）、空值/重复等边界；候选方案及不同输入的预期结果分别列出，待批准。
- 当前行为：用户报告 `123` 与 `1234` 匹配表现不同；未拿到完整测试和 SQL，不是复现实测结论。
- 技术设计：选择与已确认规则等价的机制；需要考虑分片范围、参数、分页与调用契约；尚未验证的选型不得标已确定。

完整样板见 10 案例 B。这里没有将一次解释重写四份文档，只是让不同性质的内容占据正确的语义位置。

## 3. AI 内容生成协议与评审循环

生成时读取表达契约及目标问题，从批准知识与允许读取的资料中取得事实；先列清楚依据与必要未知，再组织面向人的内容。输出结构稳定：目标/内容类型、正文（适合自然文字和表格）、引用、适用范围、关键疑问、建议变更、对应精确版本。平台检查越层混写、未解析引用、缺少条件/结果、重复与矛盾；无法形式化的语义，由独立评审 Agent 或人按质量准则判断，生成可读修订意见。人提意见时绑定段落/规则行/知识修订；Agent 应保留已正确部分和既有约束，只对认可的变更修订，不追逐最新反馈而推翻旧规范。

建议把表格/段落锚点与内容结构绑定，而不是存一份没有引用的 AI 摘要。展示文字允许去重、压缩和本地化；必须保留关键分支、例外与证据访问方式。没有证据的生成解释只能为候选；输出内容应可区别“系统已经知道”“Agent建议”“仍未知”。

## 4. 认知质量评价：不是一个分数

| 维度 | 可核验问题 | 检查方式 | 失败处置 |
|---|---|---|---|
| 真实性 | 核心事实和结论是否有足够依据 | 引用存在/精确版本检查 + 专家独立核验 | 错误/无依据→阻断正式发布相关结论 |
| 语义清晰 | 需、规、行、设、实现是否混淆 | 类型规则/字段检查 + 语义审查 | 拆分或标记冲突 |
| 信息充分 | 所需判断、前提、默认和异常是否齐备 | 对照表达契约及认知任务 | 不足→缺口，不虚构完整 |
| 可判定 | 给新案例是否能得出可靠预期或明确未知 | 决策表覆盖与读者独立判题 | 反例失败/歧义→返修 |
| 一致性 | 与批准基线、其他规则、职责是否矛盾 | 结构化冲突检测 + 跨规则审阅 | 冲突阻断适用范围内的权威规范发布 |
| 可追溯 | 每个关键结论能否回到来源和版本 | 证据引用、权限、来源身份及失效检测 | 不可核验→标未知或受限 |
| 可读性 | 是否先解释结果和判断，操作负担小 | 无提示的真实读者任务 | 重组表达；不删语义 |
| 可用性 | 能否支持设计、开发、测试与变更 | Agent 任务结果与实际验收 | 生成缺失的规则/关系/例子 |

使用结论类型：**满足、缺失、矛盾、待验证、不适用**。评分可以用于试点对照，但不定义全局“认知完整度 90%”。分母是事先明确的任务/调查范围，不是知识对象总数。关键高风险未知阻断批准或验收；非关键未知可明确风险后进入待处理，不把整个项目因一个术语未定义卡死。

## 5. 认知呈现模型

内容模型决定要表达什么；模板决定组织顺序；展示选择合适文字、简表、案例、分段列表、变化对照和来源链接。不以格式化美观替代事实检查；人应在 1–2 层深入访问证据而不必识别内部 ID。默认不显示结构 JSON、谓词名、全量关系候选和大量状态标签。高级详情可查看。无需自动绘图；复杂流程用阶段与分支文字表达且保留状态、条件、回流和异常。不要求每个知识单元固定高度、固定表字段或必定有图。
