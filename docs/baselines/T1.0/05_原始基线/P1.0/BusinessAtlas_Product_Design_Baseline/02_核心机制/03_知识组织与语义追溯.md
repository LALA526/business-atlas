# 03｜知识组织、统一语义与跨层追溯规范

机制 M1/M2/M5。状态 R；继承 V1.2 稳定身份、读写上下文、事实级别与历史不变量。目标：一个项目是由单元、明确关系、上下文和版本组成的知识空间，而非一棵巨大的树，也非一个没有语义标签的图。

## 1. 项目如何组织

采用「项目边界 → 认知骨架 → 独立知识单元 → 语义关系 → 知识组合 → 阅读/任务投影」。

- 项目边界限定授权、领域范围、负责人、来源、基线和生命周期；全局目录可查找项目但不能跨项目泄露内容。
- 固定五维认知骨架帮助发现知识缺口，允许按项目配置扩展目录。目录是索引，一个知识可出现在多个视图，绝非事实归属的唯一方式。
- 业务能力/功能是常用阅读主轴。以业务目的组织功能，而非优先按 API 或数据表命名。技术型项目允许用组件/系统作为主轴。
- 独立知识单元负责稳定身份与语义。内容及关系可以独立修订；被同一项目的其他章节引用。
- 组合把相关规范、条件、例子、技术依据、未知组织成针对问题的完整解释。组合引用真实修订，不设第二套权威规则。

### 组合示例（EX 数据，仅用以说明）

功能「应用非标参数」：其目的引用 EX-REQ-01，术语引用 EX-CON-01/02；规则引用 EX-RULE-01/02/03；正反例引用 EX-CASE-*；实际行为引用经核验的观察（本例尚无真实观察）；实现设计引用 EX-DES-01。另一个功能「检查参数重复」也可引用 EX-RULE-03。规则改变只修订 EX-RULE-03，在发布时检查两个功能的组合与验收是否需复核，不能把两个功能页面并行改写为两条不相同的规则。详见 10。

## 2. 核心对象的逻辑合同（不是表设计）

| 概念对象 | 最少承载的信息 | 必须明确的关系 |
|---|---|---|
| Project | ID、定位、范围、Owner、默认阅读上下文、当前发布基线 | 所属知识、成员、任务、来源 |
| KnowledgeUnit | 稳定 ID、类型、项目、名称、语境、职责、标签 | Revision、关联单元、适用性 |
| Revision | revision ID、unit ID、类型定义版本、内容/断言、创建人/时间、依据 | 前序修订、来源、ChangeSet |
| Assertion | 主体、谓词、宾体或值、条件、资料性质、核验、证据 | 精确版本、证据、是否冲突 |
| Relation | 关系身份、类型、方向、两端及必要定位、适用条件、证据 | 两端知识身份；批准快照绑定两端修订或解析规则 |
| Rule | 目标、适用情况、输入、条件与比较语义、结果、优先级、默认/异常、例子 | usesFact、constrains、realizes；来源和批准 |
| Flow / Transition | 阶段/节点、真实顺序及分支、guard、状态、结果、异常/回流 | 行动、参与者、规则、数据影响；保留身份 |
| Source / Evidence | 来源ID、修订、定位、时间、方法、可见性；支持/反驳何项结论 | 断言、观察、Agent Run |
| Decision / Issue | 问题、涉及的知识/任务、推荐与依据、责任、状态、决议 | 背景基线、应答与后续修订 |
| ChangeSet / Baseline | 原基线、候选修订与处置、依赖、审批、发布范围；基线成员 | 历史基线、提案、决议、交付记录 |
| Task / Delivery | 意图、变更目标、保留约束、调查记录、验收、实现/测试/知识状态 | 知识引用与版本、交付证据、PR/Manifest/部署 |
| View/Profile | 认知目的、根对象、需要的内容类型/顺序、展开点、适用角色 | 真实修订与来源；不是事实本身 |

这些不是强制一一对应数据库表。业务规则如有多个不可分割的判断行，可在同一 Rule 中保留稳定行 ID；被多个规则复用的比较语义则抽取为独立领域概念/规则。粒度由维护和审核边界决定；禁止将每个句子拆成实体或将整个项目塞成一个富文本。

## 3. 关系词典：这才是追溯与影响分析的依据

建议以下核心关系；必要时与 V1.2 现行谓词做明确映射，不能直接新增同义谓词造成两套语义。每条关系允许条件、来源、核验状态、版本和说明。逆向查询是相同关系的另一读取方向，不存两份真相。

| 关系 | 从 → 到 | 语义 | 变更调查方向/风险 |
|---|---|---|---|
| contains / belongsTo | 领域/能力 → 功能/对象 | 归属或聚合，不等于执行 | 用于界定范围，不自动传播所有成员 |
| defines | 术语/定义 → 概念/属性 | 给出语言含义 | 定义改变，检查全部引用及歧义 |
| specializes | 概念/规则 → 上位概念/规则 | 细化，必须声明继承与例外 | 检查继承条件，非自动覆盖 |
| refines | 详细需求/规则 → 上位需求 | 解释怎样满足抽象目标 | 逆向查受约束规则；正向审视原目标是否仍满足 |
| usesFact | 规则 → 业务属性/事实/概念 | 判断依赖的事实 | 属性变更反向查规则，规则变更查输入需求 |
| constrains | 规则/不变量 → 行为/对象 | 规定允许行为或状态 | 检查所有适用行为；不是执行先后 |
| performs | actor/组件 → action | 履行业务动作或系统操作的责任 | 职责变化查授权、接口、角色 |
| triggers / followsWhen | event/action → action/node | 有证据的触发/执行顺序或分支 | 仅真实执行关系可叙述业务顺序 |
| changesState | action/transition → state/object | 触发状态变化 | 查合法状态、事件、边界与例外 |
| satisfies | 行为/能力 → 需求 | 满足目标的一部分 | 行为变更回查目标，不代表已经验收 |
| implements | API/组件/操作 → rule/action/design | 具体实现映射 | 正反向均调查；不能证明合规 |
| mapsTo | 业务属性 → 物理字段/表达式/API 输入 | 业务含义的技术承载 | 数据字段改变反向追溯属性，再追规则 |
| calls | API/组件/操作 → API/组件/操作 | 有证据的调用 | 方向和版本/条件必须保留；检查所有调用者 |
| reads / writes | action/operation → 数据/字段 | 数据读写及副作用 | 查数据一致性、调用者、迁移回滚 |
| dependsOn | 组件/要求/知识 → 组件/知识 | 依赖约束；须细分依赖目的 | 若只知一般依赖，列为需调查，不当直接影响 |
| governedBy | 对象/设计 → 约束/决策 | 受哪项已批准决策制约 | 识别职责漂移、技术约束 |
| validates | 案例/测试 → rule/requirement | 验证对象和预期 | 规则变化复核正反边界及回归；不等于通过 |
| observedAt | 观察 → 版本/环境/运行实例 | 观察的条件 | 版本不同要求复核，不直接沿用观察 |
| evidencedBy | 断言/结论 → Evidence | 支持/反驳依据 | 证据撤回/变化时复核，不自动改变规范 |
| supersedes | revision → revision | 已批准的更替关系 | 保持旧引用和历史，禁止循环 |
| conflictsWith | 断言/规则 → 断言/规则 | 有条件的矛盾 | 记录双方、范围和处理决定，不静默合并 |

禁止：无证据把两个同名对象合并；用 containment、dependsOn、implements 画出或叙述不存在的业务执行顺序；所有关联邻居全部拷进任务；以“未找到关联”宣称无影响。对 `reads/writes` 等，仅在证据授权范围内展示。反向追溯需要关系两端的稳定身份、语境和版本。

## 4. 项目知识的读取、组合与约束

**读取上下文**：project、主体/当前权限、目的、基线或草稿/历史模式、环境/组织/业务类型/时间、目标根对象、语言。缺省为当前发布基线；明确历史版本不可悄悄回退最新；草稿必须视觉与语义隔离。历史内容不可变，但权限按当前策略重新判断。上下文不足时，报告缺失/冲突，不擅自取一个版本。

**组合规则**：以“认识这个功能”作为任务，先取根、目的、参与角色、适用的业务需求/规则，解析 flow guard 和决策节点中的规则引用，核对必要事实；按实际业务过程组织判断和结果；再取技术映射、观察差异、例子及证据。对于不足以回答的问题，保留未知/受限状态和后续获取方式，不展示潜在敏感对象 ID/数量。读取默认最小必要范围，详情可选择展开；既不能全图无界读取，也不能因默认列表只显示一页就丢关键条件。若关键链受限或未建模，输出“当前上下文不能充分回答”。

**任务组合**：新需求/缺陷只给初始意图；关联功能可选。结合已批准基线、规则链和最近观察得到候选变化，调用 06 进行调查。保存需要保持的规范与职责引用、差异和验收，而非复制完整产品文档。实际采用的 Task Context 固定版本，新的批准修订、源代码变化或权限变化可触发失效；必须重新基于有效基线决策后才能继续执行。

## 5. 身份、版本与一致性不变量

1. 项目内稳定 ID 与显示名分离；外部 ID 用来源命名空间映射。改名不是删除再建。
2. 业务概念与技术物理字段是独立知识身份；字段改名/替换不自动改变概念。
3. 历史修订不可变；关系也有修订历史，基线发布不能只换一份正文而丢旧边。
4. 批准规范状态不能从引用传播为已核验观察；引用的存在不能证明实现正确。
5. 基线成员和关系必须一致。必需引用不存在、未批准、权限不足或适用性冲突时，正式阅读/执行要明确失败或不完整，不静默丢弃。
6. 删除业务知识通常是废弃修订，历史保留；真正敏感数据删除遵循独立授权与留存政策，不许从旧版本泄露。
7. 重导原资料保留外部身份、等价内容幂等；不同材料对同一事实矛盾则生成冲突，不按最后导入覆盖。
8. 一条知识的所有呈现必须能定位同一版本；若同时显示历史和当前，标明版本区别。语义和展示布局独立。

## 6. 为什么这样设计能够支撑字段增减

示例：字段 F 承载业务属性 A；R1/R2 的判断使用 A；动作 X/Y 被规则约束；它们共同满足目标 Q；API P 及测试 T 与动作或规则相联。修改 F 时，候选追溯方向为 F ← mapsTo ← A ← usesFact ← R1/R2 → constrains → X/Y → satisfies → Q，且沿实际 reads/writes/calls 查 P 与其他调用者。调查不能只停在 R1；若 R2 使用隐含推导（资料缺关系），需 Agent 搜索真实证据补充。结论可能是业务语义不变、只更换映射；也可能需要变更现有规则。目标 Q 保持除非获授权修改。完整推演见 10 案例 C。
