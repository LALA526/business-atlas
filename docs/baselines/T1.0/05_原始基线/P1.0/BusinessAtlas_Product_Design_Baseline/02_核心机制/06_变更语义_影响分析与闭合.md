# 06｜变更语义、影响分析、传播与闭合

机制 M5/M6。状态 R。解决现实问题：业务需求通常抽象，修改一处字段、参数或代码可能打破多个业务规则；本机制以完整目标行为及保留条件定义任务边界，不以用户点名的位置定义。它可以成为独立的认知服务，但必须明确服务的输入、输出、调查证据与边界。

## 1. 先判断是哪种变化

| 变更类型 | 示例 | 默认处理方式 |
|---|---|---|
| 目标/范围变更 | 搜索应从精确匹配改为子串匹配 | 由业务 Owner 确认；展开受影响规则与行为 |
| 领域语义变更 | “重复参数”定义发生变化 | 查术语使用、判断依据、业务约束、所有受影响功能 |
| 规则变更 | 新增审批条件，或移除匹配分支 | 对照条件域、结果、优先级、默认及异常；业务审批 |
| 实现映射变更 | 物理字段改名或以等价数据传递替代 | 业务语义默认保留；核验等价、所有调用方及迁移 |
| 职责/接口变更 | 决策从应用层移至其他组件 | 查设计不变量、授权、接口和失败语义；技术 Owner 批准共享职责变更 |
| 证据/观察变化 | 发现旧文档与运行结果不一致 | 更正观察、复核符合性，不自动修改目标规范 |
| 技术清理 | 去掉无效兼容、重复查询 | 证明行为等价，检查副作用、兼容与调用者；授权范围内主动决定 |

业务意图不是具体实现；技术请求也不自动授权业务行为变化。变更输入可只是一条自然语言需求、目标知识 ID、设计方案、代码 diff 或发现的问题。平台/Agent 将其转成可审核的变更语义合同。

## 2. Change Intent / Task Semantic Contract（变更语义合同）

以下内容为内部完整结构，不要求人手工填。适用复杂程度按风险和影响决定：

| 内容 | 最小要求 |
|---|---|
| 意图与来源 | 希望解决的问题/结果，提供者、原话/来源、发生范围；未解释清楚时标待澄清 |
| 现状 | 基线、相关已批准规则、观察行为、已有设计和职责（分层） |
| 目标 | 具体要改变的业务情况、判断与结果；若纯重构明确行为应维持 |
| 语义差异 | add / revise / retire / preserve / revalidate 的项及各自的修订引用 |
| 保留约束 | 不变的业务目标、适用范围、业务判断、数据语义、权限、职责和兼容契约 |
| 调查边界 | 必要检查范围、已检查依据、未能覆盖和高风险未知 |
| 处置决定 | 各真正受影响项的变更/保持/复核/废弃/转交方案、原因与责任 |
| 验收与回写 | 预期业务案例、回归、实际证据要求、知识修订包、发布与对账状态 |

即使用户只说“删这个 TVP 参数”，也先调查原行为、该参数的业务含义与目标；如果已经批准规则无需改变且有等价实现，可在授权内确定技术选择。如果参数代表的业务判断要消失且无明确授权，提出待决问题并给出建议，不直接改规则。无关键需求信息不生成看似可执行的合同。

## 3. 影响分析（Impact Analysis）的完整工作过程

| 阶段 | AI/系统负责的工作 | 具体产物 |
|---|---|---|
| IA-1 识别目标/基线 | 区分请求原话与真实目标；读取有效批准基线、代码/观察版本，找未决冲突 | 根对象、变更类型、目标与保留项、分析上下文 |
| IA-2 语义候选发现 | 从被改变的概念/字段/规则/行为开始沿有意义的关系双向追溯；包含决策节点/guard、适用性、共享规则 | 候选项、明确路径、关系语义及不确定性 |
| IA-3 证据调查 | 根据风险扩展真实源码/接口/数据/文档/配置/历史决定/测试的搜索；寻找未建模的隐式调用方、旧兼容和运行入口 | 调查过的范围、来源版本、搜索方法、命中/非命中、覆盖限制 |
| IA-4 影响判定 | 对比新旧语义和职责：该项是否真的需要修改？为什么？无需修改凭什么？是否改变业务结果？ | required / potential / no-change / deferred / unknown，建议处置和证据 |
| IA-5 方案收敛 | 评估业务和技术方案，优先完整链路、职责一致和维护简单；对等价冗余主动消除，记录决策 | 推荐改动、需要人批准的决定、保留约束、任务范围 |
| IA-6 传播与复核 | 对新确认的影响或拟修订规则再按 IA-2~5 检查依赖；关注冲突、复用规则与迁移顺序 | 一批协调的 ChangeSet/工作项，以及重新核验列表 |
| IA-7 冻结执行上下文 | 经必要业务/技术审批，固定知情版本、完成条件和必要接口所有权；并发变化需再基线化 | 已明确可执行的 Task Context / 部分阻断原因 |
| IA-8 实施后验收 | 实际 diff、测试、运行/交付证据与目标/保留项对照；发现遗漏重新进入调查而非只改测试 | 完成或返修结论、知识变更、债务与已部署版本对账 |

**候选 ≠ 已调查 ≠ 真受影响 ≠ 已修改 ≠ 已验证。** 任何阶段不得通过赋予一个标签假装完成后续阶段。I/O 合同见 07；人默认查看浓缩结论与必须决策事项，不逐行填候选表。

## 4. 候选发现和证据调查的限制

使用 03 的有语义关系作为种子。候选遍历需按关系类型与上下文选择方向，检测循环并记录范围；出现广泛关系时按风险和关联语义分层扩展。不能固定只走三层后宣称完整；也不能无限遍历全部项目并把可达对象全部判为必须修改。迭代传播直到**当前确认的待处置集合稳定**且必要调查项结清，或明确预算/证据不足而输出未闭合范围。迭代收敛不证明所有未知依赖都被发现。

涉及真实代码需调用有权限的调查工具或由人提供证据。对比旧新接口、所有入口/调用者、业务判断、状态及数据流、旧路径、配置与功能开关、异常/并发/事务、迁移/回滚、测试、文档与部署。此列表作为内部按风险选用的调查轮廓，不是十五项必填空表。隐式 SQL、反射/动态调用、外部消费者、运行配置可能无法静态判断；记录真实证据覆盖与缺口，不将“搜索没有命中”当作全世界无影响。

### 影响记录（每个重要项可追踪）

`影响 ID；根变化；目标知识/技术对象精确版本；候选路径；关系语义；调查范围和来源；判定；理由；处置；责任/任务；验收证据；状态；仍未知的风险`。

- required：已有证据表明目标/保留约束受到影响；需明确变更和验收。
- potential：只有有意义的关联线索，需调查；不能直接要求修改。
- no-change：已在明确范围证明无需改变，或等价行为得证；保留证据。
- deferred：有实际影响但由明确责任人及关联 Task/时间处理；若阻断当前业务行为，不允许将其当普通推迟完成。
- unknown：资料/权限/分析不足，具体说明缺何证据；高风险未知阻断批准或完成。

## 5. 变更传播与审批

作用对象是语义和版本，不是批量改字段的脚本。每次变化可能使其他知识：新增、修订、废弃、保持、重新核验（内容未变但依据过期）。例如技术字段改名，业务属性和规则仍保持；映射修订，实际观察和测试需重验。删除承载关键业务事实的字段时，先判断能否以等价事实替代，若不能则须批准相关多个规则及验收的变化，不能只删一条规则。

传播同时处理向上目标（原业务需求仍满足否）和向下实现及案例（原有行为怎样保持/验证）。每个影响结论均可回到具体需求、规则或职责。变更审批按相互依赖的知识组进行；部分确认可以先保留，存在必要依赖时不允许半发布。实际采用新规则的时间与代码/部署版本独立对账。

## 6. 决策权与 Agent 工程判断

当代码可证明 A 是 B 的子集，且 UNION 的去重、投影、排序、空值、权限、分页、错误及副作用语义等价时，A UNION B ≡ B 可成为消除冗余的技术理由。不能仅凭集合式忽略 SQL 或调用语义。Agent 应调查并给出建议、证据与验证，在授权内完成等价清理；若业务范围、兼容承诺或职责变化则交授权 Owner 判断。不要用“你坚持就照做”逃避工程责任，也不要用“更简单”擅改规则。

## 7. 变更闭合性（Change Closure）的验收合同

| 检查项 | 可完成所需证据 |
|---|---|
| 目标正确 | 已批准目标和实际行为对照；不得以代码 compile 代替 |
| 保留约束 | 原规则、职责、数据范围、外部契约、权限等未被破坏；回归或等价证明 |
| 影响处置 | required 已交付；高风险 potential/unknown 已解决或经明确风险授权且不破坏必要条件；no-change 有证据 |
| 调用链/数据流 | 所有已确认相关入口参数、映射、处理、输出与错误一致；旧路径和迁移明确 |
| 冗余处理 | 需要消除的重复与死路径已处理；必要兼容有理由和去除计划 |
| 验收 | 业务正/反/边界/旧行为测试；实际运行结果绑定代码和环境 |
| 知识交付 | KnowledgeChange 与最终 Merge Manifest 关联，知识审批/发布、部署对账可追溯 |
| 遗留问题 | 未验证项、债务、风险、Owner/处置明确；不可把阻断项隐藏在备注中 |

普通紧急例外由授权人明确批准并设处置期限，标记部分交付/知识债；即使代码合并也不能将未通过整体门槛的 Task 标为“完整交付”。决定、变更和证据更新均保留审计轨迹。
