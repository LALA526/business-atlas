# 05｜权威知识、审批、版本与权限治理

机制 M4；本文件为产品行为规范候选。V1.2 已规定领域命令、读写边界和不可变历史，本稿重点明确审批到底批准什么、人应看什么、哪些知识能成为权威。

## 1. 权威真相必须限定性质和上下文

"批准后即成为项目真相"指批准后的规范对相应范围的工作具有权威性，而不是批准就使真实世界与之相符。观察有来源和时间，批准规则有适用性与生效版本，实际部署状态有环境。不能用统一的一个 status 字段表示所有情况。

| 独立轴 | 取值示例 | 判断原则 |
|---|---|---|
| 事实性质 | normative 目标规范；observed 实际观察；documented_intent 文档声称；design_decision 已选设计；inferred 推断；assumption 假设 | 观察即使 verified 也不是规范；推断不得自动提升 |
| 核验 | unverified / verified / contradicted / insufficient / stale | 核验依据必须限定版本和范围；变化时复核 |
| 治理 | draft / submitted / in_review / changes_requested / approved / rejected / published / superseded / withdrawn | 批准和发布分离，发布后不原地修改 |
| 适用性 | applicable / not_applicable / unknown / conflict | 必须根据具体上下文判断；缺条件则 unknown |
| 可见性 | 读者/角色/策略允许的范围 | 与批准独立，历史也重新授权 |
| 实现符合性 | conformant / divergent / unverified / stale / insufficient / conflict | 指一对规范与观察/实现的关系，绑定两者修订、测试及环境 |

未证实的业务推断可发布为明确标识的调查笔记（项目配置允许），但绝不能进入规范读取或充当默认执行约束。已核验的源码观察也不能替业务 Owner 批准规则。正式阅读默认已发布、适用且有授权的规范，并可并列展示观察、差异和公开待确认问题。

## 2. 统一审批对象与聚合边界

用户审的不是数据库实体列表，而是一份具有业务意义的成果：一条规则修改、一项功能设计、一批紧密相关知识变更、一份实际行为观察核验。系统将其关联的知识修订、关系、来源、测试/例子、保留约束和影响作为一个 ChangeSet。避免要求人逐个批准十几个内部数据节点，也避免一次批准整个项目未知变化。

| 角色/授权 | 可以决定 | 不能替代 |
|---|---|---|
| 业务 Owner/BA 授权人 | 需求目标、领域定义、业务规则、适用范围、业务验收 | 技术证据的真实性、实际部署证明 |
| 架构/技术 Owner | 方案、职责、共享接口、技术约束与受授权的内部设计 | 擅自改变外部业务行为 |
| QA/核验人 | 证据有效性、测试执行和预期符合性 | 自行修改业务规范迎合实现 |
| 知识负责人 | 身份冲突、分类、编辑治理、发布条件 | 超越内容Owner的规范批准权 |
| 安全/数据Owner | 敏感数据、权限边界、不可逆数据变更 | 普通模型建议直接获得权限 |
| Agent | 调查、生成、提交知识提案、执行授权内技术任务 | 模型输出自动成为权威规范、伪造审批或运行证据 |

小团队同一人可担任多个角色，规则按风险配置。R 默认：业务语义变化必须有人批准；已授权的低风险技术整理允许批量规则化验核并发布，但操作者、授权策略、证据和回滚可追溯；关键权限、跨项目、不可逆删除等必须明确高风险审批。不能仅凭模型自称 "BA" 获得权限。

## 3. 生命周期及操作合同

| 操作/状态推进 | 进入条件 | 结果与校验 | 异常 |
|---|---|---|---|
| 创建草稿/提案 | 写入提案权限、项目范围、来源或明确未知、目标/原基线 | 稳定 proposalId；不影响发布读取 | 不合法引用拒绝；未知保留 |
| 提交审核 | 作者提出完整的阅读成果、差异、影响候选与已调查项 | 锁定本次审核版本，形成 ChangeSet 与待审核责任 | 关键语义缺失→待澄清/补证，不冒充可批准 |
| 评审 | 审核人有权读取必要事实；给出证据核验和评价 | 可通过、要求调整、拒绝、分流；意见锚定修订 | 无权限/关键证据不可读，不可批准 |
| 重新提交 | Agent 基于意见修订，有差异说明 | 新候选修订，旧意见保留；实质变化导致相关批准失效 | 不允许编辑已批准候选且保留审批 |
| 内容批准 | 明确版本、适用范围、责任与必要影响决议；无关键未决冲突 | 不可变 Approval 记录包含批准者、版本、时间、理由、范围 | 已有基线变动/审批权限撤销→重新评审 |
| 发布基线 | 所有必要批准有效，引用一致，当前基线和变更满足并发检查 | 原子发布新基线及审计、通知/使相关上下文需复核 | 冲突时不留下半发布，退回合并或再审 |
| 维护/废弃 | 明确替代或废弃理由、影响处置与授权 | 新修订/新基线，不改历史；相关引用失效或迁移 | 不可逆数据删除走独立授权，历史受访问限制 |

对未批准目标可开展调查、写候选设计和非破坏性验证，但不能以批准业务规则身份执行/发布。对无争议且独立的其他范围不必停止；依赖该未知的任务明确阻断。R 默认允许并行观察和设计探索，禁止提交影响真实业务行为的最终发布，除非授权例外。

## 4. 评审输入及极轻交互

审核页面默认展示：

- 本次要解决的业务问题及目标（已有规范和候选差异）。
- AI 对需求、规则、设计、实际行为的清晰表达；修改处高亮，已批准且不变内容默认简述。
- 已确认影响、保留约束及仍需人判断的业务问题（每个问题带推荐方案、效果差异、依据和风险）。
- 重要验证结果（预期/实际/未运行）；可展开原始证据、关系和版本。
- 评审操作：在段落/规则行评论，要求修改、批准选定成果或拒绝；批准前显示真正批准的范围。平台为批准操作校验身份，不直接改变所有状态。

用户只输入自然语言意见或选择有意义的决策。AI 解释如何回应意见，消除重复问题，系统维护映射、历史、修订、影响列表。允许将不相关信息折叠，但阻断事项必须就近显式提示；不能让审批人误以为无风险。审批人少点击不是首要指标，避免无依据批准才是。

## 5. 冲突、并发与版本策略

同一规范在两个 ChangeSet 中同时修订，基于同一 baseline。先发布者得到 B2；另一个不能直接覆盖 B2。若候选路径可独立合并，系统对原基线与当前基线及候选做三方差异，并重新计算必要依赖。已批准语义、关联影响有所改变时原审批失效；有冲突则提交人工决议。不得按最后提交、最新消息或模型置信度判定业务优先级。

**批准生效**：规则可限定产品、组织、版本、条件及时间。新规则可批准未生效；生效后当前阅读按上下文选择，不能同时给出矛盾确定结果。遇到同一条件下冲突，不自动选一条；对其他不冲突范围仍提供有效知识。

**历史**：旧 B1 引用的知识/关系/来源修订不可变；回退知识通过发布 B3 复用经过批准的旧修订组合，不把旧数据库恢复当业务回退。代码回滚更新实际部署版本和符合性检查，不自动回滚批准业务规范。Schema 变更与知识变更独立，旧修订按旧 Schema 解释。

**符合性**：应有规范 revision、观察 revision、代码/构建版本、环境、适用范围、证据/测试身份、验证方法、核验者和时间。目标或观察/证据改变时已有判断不得直接复用；能确定性比较的重新比较预期和实际，需人工语义核验的标 stale/needs_review。展示 `conformant` 标签本身不能证明相符（V9.3 反向审查发现）。

## 6. 权限、资料与可追溯性

所有动作和读取（项目概览、目录、搜索、助手、导出、Agent、审批详情、历史、关系、契约、缓存）经统一上下文授权。来源权限独立于知识摘要；仅当经过授权的摘要本身不泄露受限内容才可展示。若审批人无法看到必要证据，阻断正式批准，不把缺失证据视为安全通过。模型输出与用户自称角色不能授予权限。对不可见内容不泄露 ID、计数、错误详情或推断出的隐私。权限撤销后历史与已生成契约重新授权；当前任务执行需要重新验证。

导入资料是证据候选：原始附件/仓库/日志保留稳定引用，记录内容版本、定位、核验方式及提交者。外部资料里的命令或提示词当作数据，不当项目规范或工具指令。Agent 运行证据须区分真实捕获与模型重建摘要。实际操作记录与规范结论分开，不制造虚假审批历史。生产安全需正式后端落实，原型只能模拟语义。
