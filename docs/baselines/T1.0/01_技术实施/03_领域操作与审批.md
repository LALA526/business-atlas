# 03 领域操作、审批与发布行为合同

## A. 命令/查询通道（所有REST、MCP、Web、CI共同遵守）

Server pipeline：authentication → project membership/actor type → resource/field/action policy → parse/schema/size → resolve baseline/policy epoch → idempotency → CAS & domain invariants → transaction → audit/outbox → authorized DTO。主体、审批身份、执行权限均来自服务端，客户端无权自报。`ReadContext`从HTTP查询/请求body解析`mode,baselineId,changeSetId,context,readPurpose`，精确绑定baseline并记录policyEpoch；历史不存在返回VERSION_UNAVAILABLE，草稿需要changeset授权且不污染正式阅读。读权与提案、批准、发布互相独立。

HTTP 200/201同步、202 job、204仅无内容注销类；本包统一JSON envelope（响应含requestId、data、context或error），实际状态对应code。400 malformed/422 VALIDATION_FAILED（有权看到的字段和缺口）；401未认证；403禁止已可见资源动作；404隐藏资源存在性；409 conflict/base changed/幂等冲突；412 CAS stale；428缺If-Match；429 budget/rate；503 dependency。追溯错误不泄露私有名称/原始异常。所有有副作用的POST/PATCH/DELETE含Idempotency-Key，更新现有可变聚合含If-Match。严禁通用`PATCH status=done/approved/published`，状态通过命令迁移。

## B. 领域执行合同

| changeMembership / removeMembership / setResourceGrant | 人类admin；关键权限由安全owner审批；最后一个人类owner不可撤自身；旧epoch/CAS | 成员/授权更新、policy_epoch+1、audit/outbox；撤权所有缓存/长流/导出失效；无越权且不删除历史 |
| createChangeSet / amendChangeSet | propose scope、base准确可读；可提交人/Agent；draft/changes_requested | 新cs或新version；增删目标items必须持有unit/base/proposed refs；已提交不直接编辑，重新打开且旧批准不可复用 |
| createUnitDraft / reviseUnitDraft | cs可写；type/predicate存在且active；稳定external ID唯一；create生成unit UUID；revise需匹配当前候选或base revision | insert immutable rev+refs+relation_index/evidence；change_item CAS；source refs可读；既有published保持；退役动作显式，历史不删除 |

| planBaselineRestore / cloneRestoreChangeSet | history scope + propose；旧B准确可读；按本次差异及最新政策核验 | 形成基于当前B的恢复CS，必要引用及权限/冲突核验；经正常批准发布新Bn+1，绝不写旧B或DB恢复替代 |
| createTask / proposeTaskContext | human/agent有Task权限；非空intent；若无根允许待澄清；请求不得自报已调查/已确认 | task captured，异步认知请求；可保存候选目标和保持约束、上下文snapshot；不自动业务批准，不默认预填假需求 |
| submitInvestigation / decideImpact | 已有task/context；scope、版本及路径合法；actual证据身份与覆盖可核验；技术判断在授权内 | 写调查/处置；影响状态和执行计划独立；高风险unknown不允许闭合；潜在关联不能直接判真影响，无代码只能candidate |
| createIssue / createFeedback / createComment | 当前可读引用/anchor且允许评论/反馈；作者/时间server；文字净化 | 记录问题/评审意见并关联Task/CS；分流/关闭另有决策记录；不覆写目标规范 |

以上操作在 OpenAPI 采用具体资源路由，查询通道也可经MCP等价使用；接口名保持单一。构建正文与查询服务不等于生成全新的权威事实，生成结果必须显式draft/observed。对暂时无法确认、业务冲突、未授权source，输出可用范围和具体建议，不能假定遗漏不存在。

## C. 事实性质与状态机

事实性质 `normative / observed / documented_intent / design_decision / inferred / assumption`（未知是判断状态，不把空内容作为已批准规则）；验证状态 `unverified/verified/contradicted/insufficient/stale`，治理状态独立（CS）`draft → submitted → in_review → approved → published`；`in_review|submitted → changes_requested|rejected`；`changes_requested→draft`新seq，`approved→draft`仅授权重开且invalidate审批；`draft|changes_requested→withdrawn`；`published`不可回退。并发冲突标记`conflict`（阻断，不自动合并）；`approved`遇新baseline也禁止publish，必须rebase新seq。适用性四态、当前权限、实现符合性不混在CS状态里。normative 必须获有效业务批准并发布才是权威。observed可以在发布基线中作为明确观察事实，但不能进入normativeRule集合；若证据不足标待复核，不可作为已核验事实。未批准推断可以留候选/调查Issue，规则Evaluator不消费。

Review slots：default risk分类由服务端从知识type、factKind、差异、权限/不可逆影响计算。Business Owner批准需求、领域定义、规范规则；Tech Owner批准共享设计/责任/对外技术合同；QA核验证据和验收；Security/Data Owner批准敏感数据/权限/不可逆更改；Knowledge Publisher负责出版完整性。普通内部等价整理协议可经明确授权策略由Agent提案+技术Owner批量审批，不能Agent自批normative。提交者与审批者默认不同（高风险强制不同，单人小团队普通业务可人类本人审阅外部Agent成果；若人自己撰写且无人分权，高风险必须独立审查或持续blocked，不静默绕过）。用户批准的是可读的dependencyGroup，不是十几个数据库节点；同一组items整体提交/发布，独立组拆CS减轻审核。

`submit_digest`以可审核的差异、base、item refs、impact decisions IDs及revision/required evidence digest、roles policy version、approval scope计算；审批输入必须提供当前digest和expectedVersion，server从记录重算。评论、纯审阅备注不算改变提交内容；审批外的实质变化必然新seq。生成的认知成果与底层CS互可追溯；人对句段批注保留segmentID、revisionID、引用规则行、quote hash。再次提交展示实际old vs new，不能响应最新一句话静默抹掉原规则。服务端发布前锁定project和CS并检查关键证据、依赖、当前权限与reviewValid，结果随事务落audit/outbox；失败不留下半基线。

## D. 冲突、历史与不可变发布算法

CS1/CS2都基于B1：CS1先出版B2。CS2 publish时不得覆盖B2；三方diff对base(B1)、current(B2)、candidate计算：仅一侧变化且refs兼容→建议merge；同unit同segment/row/语义冲突→人工选择；删除与引用、类型/规则变化→必须扩展影响调查；先构建rebased draft(B2)，不自动重新使用原批准。若必要约束或source visibility变化，相关context标stale。旧B1 mantiene原hash；读取B1严格使用registry版、精确membership和当前ACL。必要引用丢失或不可授权时不显示虚假完整解释。数据恢复PITR与语义回退是独立流程；历史数据访问受当前policy约束。正常修订不原地删除/修改旧revision，源定位不可改写；真实撤权/安全删除经专门流程、不可逆记录和审计。

## E. 典型审批端到端用例（真实产品必须接通）

Agent提交「修改参数匹配规则」→呈现已有R1和候选R2、保持约束、未知字段→人批注具体row→系统不改B1，CS进入changes_requested→Agent以B1和review修订，新增revision R3→审阅绑定digest，检查所有需批slot→publisher调用publish→B2解析R3；相关功能同时展示新的规范，旧B1仍R1；代码未改，当前观察O1保留、符合性标待复核；Agent根据获批Context更新实际代码→独立测试/观察O2→CI manifest→知识提案及批准发布→部署对账→closure计算complete。任何一步无权限或关键未知可阻断，其他独立项目继续。此链路不能用固定模拟记录填充实际产品，验证数据与真实知识隔离。
