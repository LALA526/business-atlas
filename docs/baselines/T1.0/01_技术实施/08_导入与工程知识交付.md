# 08 资料接入、旧知识兼容、Git/CI与真实Self Project

所属M06/M05/M11/M09。P1.0 PD-21/30/32/33，V1.2 Git协议保留其核心约束。导入、实际观察、业务批准是三种不同事件。下文以真实运行设计为要求，合成example不是已执行记录。

## 1. AKP与资料接入

保留AKP/0.1：原V9.3 `packages/schema/akp-v0.1.schema.json` 原字节保存在机器合同；V1.0 候选知识包、V9.2制造资料可用legacy adapter导入。T1 native可采用`AtlasProposal/1.0` (revision inputs + refs)，对外新增标准AKP/1.0在真实兼容测试后通过versioned adapter发布，不直接把旧0.1改名。既有visual layout不进活跃模型，独立文字注释/源图片/业务引用可保留，原始包按权限保存。不能静默删除旧数据或当成真实生产代码。

导入步骤：
1. 人在项目菜单上传或Agent经REST提交已整理包；认证、project权限、file size/content type/扩展名、hash、速率校验。私有upload staging；初始默认单包JSON 50MiB，ZIP 100MiB、解压上限500MiB/10000 entries/压缩比100:1，按授权可调整。拒绝path traversal、symlink/设备文件、嵌套压缩炸弹、可执行文件；解析JSON限制深度/字段数，外部URL不自动fetch。原始内容提示词按数据看待。附件恶意扫描失败或unavailable不得正式接入；原始文件不公开。
2. worker按formatVersion匹配Schema，做结构+业务语义验证：stableExternalId唯一、manifest来源/作用域、entity类型、assertion双方、Flow节点边/Rule refs、Source locator、factKind、适用性、外部身份namespace；旧版未声明有效范围不以导入日替代、不从UI/代码观察推断批准。将legacy `verificationStatus`映射到独立核验维度，`confirmed/approved`仅当有真实可核验导入审批记录且获重授权才继承语义；默认全部进proposal。
3. 预览新增/修订/内容等价重复/冲突/无效，保留source hash、external namespace与现有identity映射；同包同hash同project重放产生同result，不重建对象；packageId相同hash不同→409，不将同名对象合并。preview基于记下的baseBaseline，当前B变化时重新生成差异、使旧decisions失效。过滤仅显示当前有权内容；候选相互依赖时按组处理，不能因为某个隐藏reference悄悄断开业务语义。
4. 冲突可选reuse_existing（证据一致）、new_version（同身份）、new_identity（不同业务语境，须说明）、reject/needs_evidence；Agent给建议，用户只决定重要冲突，等价项自动化。必要source/identity冲突未决阻断stage。
5. 完成扫描的blob先进入不可变私有目录（按project+sha256，temp写完fsync后原子rename，防止半blob）；stage时一个DB事务生成所有unit/revision/relation/evidence/external IDs与ChangeSet items/audit/outbox；事务前检查所有引用/授权/当前base，故障全回滚；临时孤儿blob后续GC（有宽限期并重新查引用）。stage仅draft。用户可discard未提交/未发布候选，不能删除已发布历史。完整知识需要通过正常M05 review/publish。
6. 页面显示接入后阅读入口、未决问题、来源/处理记录、关联Agent run；所有source content按当前授权下载，受限source不能经包导出泄露。`GET import preview`读取不会批准。

`legacy mapping` 示例：Entity→core.unit + revision；assertion→Assertion payload/ref/Relationship（有明确谓词时转换为Relationship，原assertion locator保留）；businessStructures.flow→Flow stages/nodes/edges/guards；technicalStructures→Implementation/Component/API/DataField及相应refs；sources→Source revision+私有blob或授权repo定位；unknownsAndConflicts→Issue+source metadata；importProvenance→agent/run_event，区分真实捕获与重建。数据兼容测试必须用原包（V1.0、V9.2/V9.3代表样本）和损坏/重复/跨项目/冲突负例；不能只测试新格式。原V9.3 Self Knowledge是原型事实，不冒充正式产品自身知识。

## 2. PR候选与合并后Manifest（消除自引用SHA）

沿用V1.2两阶段：PR只包含`KnowledgeChangeProposal`，记录源任务/需求ID/本次知识变化、branch/PR、相关changedFiles+blobHash、定位、API/data/测试及未知，**不含包含自身的未来最终commitSha**；`headSha`若指含文件的提交同样循环，因此在PR内候选中不写，将head/base真实状态放CI外部artifact，候选以source blob和显式路径绑定。CI在merge后生成外部`KnowledgeDeliveryManifest`，绑定最终commit、proposal exact bytes SHA256、build digest、CI签名/验证身份、实际测试产物与source anchor resolution。合并策略squash/rebase后若anchor变化，实际最终blob重新核对；不匹配必须标needs_revalidation，不能盲沿旧hash。Manifest保存在CI artifact/可信私有blob，不写回同最终commit形成循环。

**本次重要兼容修订**：旧 V1.2 Proposal schema要求`requirementIds`匹配BA/ENG，不识别P1.0 PD-01..38；旧agent-task schema也同类限制。T1采用 `knowledge-change-proposal-v1.3.schema.json` + `knowledge-delivery-manifest-v1.3.schema.json`（来自原schema的受控版本增量，允许PD；保留旧1.2 adapter，禁止把旧example冒充1.3）。T1 tasks使用独立DAG schema；接入的CI检查脚本需支持两种已注册schema并依本次trace校验ID存在。未修改旧包字节。真正合并后需CI验证，不依赖模型自称signature。API可接受legacy envelope并按明确版本分派，未知版本拒绝/请求迁移。

### 真工程链路（以Azure DevOps为默认，不依赖其实际账户已配置）

仓库 `/knowledge/proposals/{taskId}/{proposalId}.json` 与实现PR共同提交；首次开发从bootstrap知识账本开始。每个受控PR（包括纯文档/infra）必须提供proposal或经批准的no-knowledge-impact声明+真实diff检验，不能由模型随意豁免；初始可统一要求所有PR含proposal。PR validation：1.检查branch/base/task/trace和current contract digest；2.校验schema、changedFiles真实覆盖（排除proposal文件本身，明确保留排除理由）、源路径/blob/locator；3.真实测试、禁密钥、迁移兼容、权限、静态检查；4.独立审查业务/保持项/实际完整影响；5.接入外部CI留证。合并后pipeline：checkout准确commit→重算proposal原字节哈希/最终source anchors→生成镜像与测试artifact→可信CI service identity上传manifest和实际测试结果→平台建立实施观察候选与原业务CS关联→review/publish→部署对账。任何fail保留原因和债务，不伪造成功。批准知识与CI分开；PR通过不意味着业务规范已批准。

## 3. 代码、知识、部署的对账状态

`delivery_record`唯一(project,repo,finalCommitSha,deliveryId)，manifest原始哈希、CI来源和task/requirement/knowledge proposal IDs、actualTestRefs。KnowledgeChange内部将 `normative` 与 `observed` 分开提交，业务规则须BA审批，工程事实需真实证据及核验。`deployment_record`记录environment/buildDigest/commit/databaseMigration/configDigest/deployedAt/actor/previousDeployment，不从Branch当前latest推断生产版本。`reconciliation`基于manifest、CS publishedBaseline、部署/current context、符合性/actual evidence动态计算：aligned/pending_review/divergent/rolled_back/evidence_missing。部署回滚更新deployment记录并重新核验相应规则，不把知识B从B3直接指回B1。发布/撤回源/代码变化/部署事件触发相关对账Job，幂等；未核实对账标stale。

紧急修复允许有权人审批明确范围、原因、风险/期限，记录`knowledge_debt`责任/到期/回补Task。必须保持安全/关键业务约束，缺非关键知识允许例外交付；不是产品完整完成门槛。正常正式最终发布不允许关键知识债未关闭。所有`divergent/rolled_back`处置或明确unknown，不允许无限期无对账。

## 4. Self Project的真实首次建构

首个仓库提交即维护`knowledge/`候选：P1.0原则、PD/DEC ID、T1架构/数据/接口、决策、不变量、实际变更/测试与来源。Bootstrap在首个服务尚不可用时通过Git候选账本保存真实来源，后端导入可用后按其repo/commit/source hash导入映射到Self Project（内部UUID由实际导入生成，外部ID使用稳定PD/DEC/T）。提交者和批准者明确；不能一键把候选P1.0全批准。开发过程中每个任务生成业务规则、技术设计、接口、实际观察和测试的差异，持续可读；真正发布后进入平台自身知识。用一次后续真实需求变更验证读取现有Self Project规范、调查影响、审批、代码PR与知识回写的闭环。独立CPQ试点不因自举通过免验。
