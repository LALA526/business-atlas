# 02 数据模型与持久化实现

本章与 `02_机器合同/database.sql`、`schemas/domain-v1.schema.json` 同时使用。DDL是工程迁移初始形状与关系约束，不另建与EF互相竞争的迁移链；由Migration Owner在真实PostgreSQL执行并生成等价EF配置/migration。T1初始DDL尚未在实际PostgreSQL运行，启动时必须验证所有约束与事务测试，不直接应用到生产。

## 1. 三种信息结构：身份、事实、投影

**稳定身份**：`unit` 的 `(project_id,unit_id)` 不随名称或分类变化。`kind` 标识ProjectProfile、DomainTerm、BusinessAttribute、Requirement、Rule、Flow、Behavior、Design、Implementation、Observation、Component、Api、DataField、TestCase、Source、Constraint、TypeDefinition、PredicateDefinition等；完整枚举由registry定义。每项目可扩展。原型中的Entity、Assertion、Flow、Source在一个通用Unit/Revision模型下保存，不是把一切变成任意JSON：每种类型必须具有版本化内容契约，关键引用经关系表和数据库约束校验。领域概念和实现对象分离。外部自然ID如 `RULE-01` 通过`external_identity`映射稳定UUID；导入重跑不得另建同对象。

**不可变事实**：编辑生成`revision`；作者、时间、typeSchema版本、factKind、payload、applicability、contentHash。候选同样不可原位改，退回修订另建revision。`revision_ref`作为引用索引保留精确revision或稳定目标ID；`relation_index`从Relationship payload派生带明确谓词及方向。引用索引和payload在同一事务生成与hash校验；不是两份事实。Flow的stages/nodes/edges、ruleRefs作为不可分割结构保存在Flow payload，节点与边有稳定局部ID，保留条件及回流。`evidence_link`将事实revision与证据revision定位连接。

**批准快照**：`baseline`包含project、编号、父版本、来源ChangeSet、registryVersion、hash；`baseline_entry`是稳定unit到精确revision的全量membership。有效规则必须在指定快照、已发布类型Schema、适用性及当前权限下选择。不同适用范围并行规则用独立rule identity+适用条件表达；不能对同一unit在同一baseline绑两个revision。Draft仅存在changeset中，从published读取时不合并未批准覆盖。候选读取显示明确基线和changeset version。历史保留，内容删除为retire/tombstone（发布时移除membership）；旧baseline继续能够读取经当前权限允许的旧revision。读取选择 `published`、`historical`、`draft`必须互斥。

**派生数据**：搜索index、目录、阅读Plan、任务上下文、导出都是可重建的投影。读正式事实必须回到baseline+revision，不在派生缓存保存第二份规则。任务、Issue、评论、运行和审计是独立活动轴，不改变历史baseline。

## 2. 物理表与关键字段

| schema / 表 | 主体与关键字段 | 读写职责 |
|---|---|---|
| identity.principal | principal UUID、issuer、subject、kind(human/agent/service)、active；唯一issuer+subject | 外部身份绑定；不存密码或token |
| identity.project | UUID、slug、displayName(仅工作区外壳)、owner、version、policy_epoch、current_baseline | 同名允许，slug唯一；已批准简介来自ProjectProfile revision |
| identity.membership | project+principal、roles[]、clearance、active、version | 一人可多role；撤权增加policy_epoch |
| access.grant | project、resource unit UUID、principal、read/propose、fieldPaths、effect | 对象/字段授权；deny优先；默认项目角色+分类允许范围 |
| core.unit | project+unit、kind、owner、visibility、created | 名称改动只改revision；当前可见性独立授权，policy变更有审计 |
| core.revision | project+unit+revision UUID、rev_no、parent_revision、type_key、type_version、schema_definition_revision、fact_kind、payload JSONB、applicability JSONB、sha256、actor、created | immutable；parent必须同unit；rev_no可用整数唯一但不代表公开版本 |
| core.revision_ref | source revision、ref_key、kind、target unit、target revision可选、required | 从typed payload原子产生；精确证据/观察必须固定，语义关系endpoint按baseline解析 |
| core.relation_index | relation revision、predicate、from_unit、to_unit | canonical Relationship body派生；逆向用索引，不再存另一条逆边 |
| core.evidence_link | fact_revision、source_revision、locator、support/refute、capture_kind | sourceRevision+定位精确；禁止没有证据声称verified |
| core.external_identity | source_namespace、external_type、external_id、unit | project内确定唯一；同名不自动合并 |
| gov.change_set / change_item | base_baseline、etag/seq、state、submit_digest，action及unit+base_revision+proposed_revision | 一个set包含不可分的依赖组；批准绑定确切digest |
| gov.review_decision | cs+submitted_seq+digest、actor、approval_role、scope、decision、anchor、reason | append-only；不得重写审批历史 |
| gov.baseline / baseline_entry | Bn版本、parent、cs、registry_version、digest、entry(unit->rev) | publish transaction独占写；历史禁止UPDATE/DELETE |
| intake.blob / upload | SHA256、size、storage_key、scan_status、uploaded_by、upload_expires | 对象内容私有，引用绑定project；临时对象不可作为权威source |
| intake.import_batch / import_entry | packageId、source namespace、format、hash、job、base_baseline、diff、decision、status | 解析/预览/冲突处理后原子stage；原包作为来源 |
| collab.task | intent、classification、rootUnit可选、task version、base_baseline、process state、externalRef | 空白需求不会创建完整合同；status仅运行过程，最终closure独立计算 |
| collab.issue / comment / feedback | 目标unit/revision或task/changeSet、anchor、body、state/author | 旧版本评论不可漂移至新版本；反馈分流后通过proposal变更知识 |
| collab.impact / investigation | task、target、relation path、disposition/status、inspection_scope、evidence refs、risk、reason、assigned_task | 候选/调查/处置分别标识；证据可追溯真实检查范围 |
| delivery.task_context / context_dependency | immutable context digest，project/task/baseline/policy epoch、required refs，target/preserve、status | 失效标记独立字段，不能重写内容；每次读取重授权 |
| delivery.conformance | normativeRev、observedRev、build、environment、applicability hash、expected/actual case/evidence refs、verdict | 精确版本与证据绑定；失效检查先于显示旧verdict |
| delivery.acceptance / delivery_record / deployment_record / knowledge_debt | task/context/test identity、expected与actual、manifest digest、build、deploy环境、知识基线与未决风险 | 自主CI identity提交实际证据；治理独立；closure由证据计算 |
| assistant.conversation / message / citation / provider | project、owner、root context、message kind/run、citations、provider secret ref | 可撤权；原文/模型生成区分；引用授权按message访问时重新检查 |
| agent.run / run_event | task/project、executor、context digest、state、event sequence、capture_kind、source | 真工具和reconstructed区别，幂等，失败/中断可恢复 |
| ops.job / outbox / inbox | type、payload、attempts、availableAt、lease/fence、event_id | 至少一次+幂等；不能异步替代发布事务 |
| ops.idempotency / audit_event / notification / error_pattern | subject+command+key、request hash、result_ref；审计、通知、错误模式 | 审计append-only；重复response须重授权，不在表存敏感明文 |
| read_model.search_document | project+baseline+unit+revision、title/tokens/aliases、index_version | 派生全文索引，授权前后的filter、publication generation一致；可重建 |

所有project scoped表必须含`project_id`，复合外键同时匹配project与稳定ID；关系两端不可跨项目。角色/visibility附着在稳定身份，若组织需历史权限信息仅保存审计，**实际读必须使用当前policy**。规则粒度：被多个功能复用、独立审核、独立修改或需精细授权才拆unit；简单字段或内部决策行用结构化body，稳定`rowId`，不能强迫每句话一个entity。

## 3. Schema及内容存储格式

`registry.json` 是T1内置类型、五维目录与关系词典；版本`atlas-registry/1.0`、每type v1；新类型不要求重建表。TypeDefinition/PredicateDefinition/ContentProfile是由builtin schema定义的治理对象，发布后加入该baseline的registry extension。修订保存builtin `schemaType + schemaVersion`，自定义类型额外持有已发布的 `schemaDefinitionRevisionId`（精确FK）；禁止动态执行JS/C#或模型生成代码来验证schema，只允许受控JSONSchema关键字及内建表达谓词。builtin升级携带旧版本文件可继续读取旧revision。自定义类型声明选用现有profile，新增字段允许但关键条件仍需指定。禁止同义谓词重复注册；类型变化只对新revision生效。关系类型fromKinds/toKinds校验、适用性以及引用的required合法性是应用服务负责，不仅JSON Schema。

`body`保留内容结构及纯文字segments；segment id作为评论协议，禁止用单一markdown全文替代可判定规则数据。Rule条件是小型声明式AST（见04），设稳定输入业务属性ID、比较语义、行id、默认结果/异常及来源；遇到无法形式化的自由文本规则可以阅读，但`evaluationMode=human`，不能作为机器可执行规则。观察记录的actual结果与expected独立保存。Flow节点关系引用稳定ID或精确revision；发布解析时验证节点/边指向、guard所属Rule和所有required refs；不能按数组顺序生成执行语义。

## 4. 读写事务规范

**UoW** 每次命令创建同一连接/事务；`SET LOCAL atlas.project_id`仅由认证且授权的应用层设置，事务结束清理。所有项目业务表执行强制RLS项目过滤；app服务role非owner、无BYPASSRLS、无CREATE/ALTER/TRUNCATE；对象/字段权限由M04补充。DDL使用migration owner账号不能进入API进程。全局项目目录只能通过M01隔离查询，限定当前subject membership；服务不得通过RLS跨项目探测。worker每次claim后以授权的job项目上下文执行，调度扫描用最小独立role/只允许claim接口，不获得业务表任意读权。

**防竞态**：共享聚合etag=`"{version}"`，客户端修改提供If-Match；idempotency key绑定principal、项目、operation和request digest。先认证当前主体及权限、检查幂等；同key同request返回当前重授权后的相同结果，不同request 409；新命令在事务中通过unique claim，聚合version CAS，提交审计+outbox。发布使用`SELECT ... FOR UPDATE`锁project row，锁change_set，重新验证base==current、review digest、actor授权和必要引用；按稳定ID顺序加锁。建立新baseline及entry，复制前一baseline未变化membership+应用变更组，校验完整性、计算canonical digest（按unit UUID排序，含revision hash、registry version），推进pointer、audit/outbox同一事务；不允许半发布。删除/更新immutable表SQL触发器拒绝，仅特殊经过授权的数据留存清理用隔离运维权限及审计流程，应用层不能调用。

**性能**：全量membership简洁且可复现，默认采用INSERT ... SELECT copy，基线发布只锁该project。`baseline_entry(project,baseline,unit)` PK，反查受影响基线时(project,revision)索引；`relation_index(project,from_unit,predicate)`及`(to_unit,predicate)`；`revision_ref(project,target_unit,kind)`；`search_document`在授权版本内查`tsvector`/trigram，严格keyset分页；任务和队列按project/status/time索引；时间用UTC timestamptz，业务asOf有明确zone。若ADR-T02基准不达标才允许增量实现，对外membership语义不变。避免每次请求加载全项目及其全部版本；无N+1的批量获取、已授权邻接关系按预算分页。

## 5. hash、备份、版本和迁移

hash由canonical JSON（RFC8785兼容；不允许NaN/Infinity；业务高精度decimal用字符串和显式单位，时间UTC ISO8601；对象key稳定、数组顺序仅在业务有序时保留，hash输入列出schema、factKind、payload、applicability、refs/evidence locator）。源码hash SHA256与Git blob SHA分开保存；不得将布局和展示偏好纳入语义hash。旧revision不可按新Schema就地重写。DB schema version/knowledge baseline/API version/deployed commit分别独立。

迁移先备份和dry run；expand（兼容旧代码）、backfill（持久job、断点、idempotent）、verify（计数/hash/FK/独立业务验收）、contract（后续发布去旧列，经授权）。从无数据库创建Schema+内置registry+空B0，不能填合成案例到真实项目。旧AKP/原型数据按08文档适配进入proposal；发布后旧历史不得伪造。运行时Schema升级必须同时有读旧格式、兼容性tests及受控回滚策略；不可逆迁移需完整恢复演练。数据保留或用户删除权与不可变审计冲突由数据Owner决定：默认撤权/封存、源blob定向授权删除和删除证据记录，不自动暴露历史内容。

### 补充约束（T1.0最终机器合同）

`intake.source_blob_link`把具体Source revision与私有Blob关联并在revision封闭时冻结；`delivery.proposal_intake`保存Git候选原始字节、hash、schema、任务和repo，后续Manifest引用其hash并在业务事务中核对task/repo。`gov.baseline_entry`必须引用已封闭的对应unit revision；派生search_document使用四列FK绑定同一个baseline entry。详情以database.sql为准；最终仍需真实PG migration/测试。
