# 04 领域语言、业务决策、知识表达和授权读取实现

关联 PD-02..12、PD-15/19、P1.0 02–04，M02/M03/M04/M07。**规则先于实现、项目业务全貌由共享语义构成、页面以人可读成果组织**。机器参考 `registry.json`、`schemas/domain-v1.schema.json`、`schemas/rule-v1.schema.json` 和 examples。

## 1. 领域名词是第一等知识

知识本体定义了通用概念，不替具体项目定义 CPQ/制造业的实际业务名词。域词汇以 `DomainConcept`、`DomainTerm`、`BusinessObject`、`BusinessAttribute` 保存：稳定unitId、contextKey、规范名称、同义词、定义、例/反例、单位/值域/空值口径、责任、来源及适用性。领域含义先有独立身份；物理字段、API payload、派生表达式与业务属性以 `mapsTo` 关系连接，关系持有mapping语义、版本和条件。相同名称在不同context不得强行合并；名称变化触发同义词维护而不换ID。`ResolveVocabulary`：规范化搜索词（NFC、去外围空白、大小写规范仅检索，不改变业务数据）、在授权基线中先查context精确/alias、后查相似候选；多义返回ambiguous，不自动挑第一条；source无权不显示名字/数量。读写别名的内容亦需审批，不由locally缓存定义真相。

知识关系采用P1.0 03语义词典。`refines(rule,requirement)`,`usesFact(rule,attribute)`,`constrains(rule,behavior)`,`satisfies(behavior,requirement)`,`implements(component,behavior/rule/design)`,`mapsTo(attribute,dataField)`建立核心追溯。关系是有来源的独立治理对象；逆向查询不是第二条相反事实。`contains`只用于分类/范围；`calls`为技术调用，`triggers/followsWhen`才允许表达真实业务执行；`reads/writes`不自动推导业务顺序。Assertion提供明确subject、predicate、object或value、限定、证据；规范性断言经批准生效。不同版本或上下文的观察可矛盾并存，不能盲合并。

## 2. 规则及可执行语义

每个Rule至少存：业务目的、适用情况、决策输入（业务属性ref、类型/单位/null语义）、业务行（rowId、when、比较叙述、结果）、优先策略、默认/异常、例子/source。优先策略枚举 `unique / ordered / collect`：unique多命中不同结果→conflict；ordered只有经批准明确且无相同priority的行顺序才能确定（较小priority先执行）；collect只有已批准的合并算子与输出类型才允许，多结果原样集合不代表任意选择。无明确优先策略默认unique+冲突显式；业务owner确认语义。默认分支只在全部有关条件明确false时执行，不能用缺失信息替代false。自由文字规则可保存为human_only，不能由执行器解释自然语言来自动批准结果。

**AST v1最小语言**：fieldRef（attributeId）读取context中事实；literal(type, value)明确比较类型；`exists, missing, eq, ne, gt, gte, lt, lte, contains, startsWith, in, all, any, not`；`isNull`单独区别缺键。输入未提供与空/null/空白三者独立，根据批准attribute的comparison/normalization策略处理，不从SQL NULL推测。string eq/contains默认ordinal且大小写敏感，若业务口径需ignoreCase必须写明；数值使用decimal字符串解析（禁止locale隐式格式），明确单位转换规则；日期UTC/业务时区、枚举stable code；类型不匹配返回unknown+理由，不能转换未知为true/false。不支持函数、SQL、脚本、网络、eval或模型自定义可执行语句。扩展算子经registry+测试+版本演化。限制AST深度32、节点1000、字符串单值64KiB，防止DoS；超过返回validation，不降级假成功。

求值真值使用 T/F/U（缺事实）、C（冲突，由规则选择/输入来源冲突产生）。all只在有明确false时false，否则未知保留；any只在有true时true，否则未知保留；not U仍U；C是阻断（不能被短路隐藏关键矛盾）。priority行评估先记录所有候选及适用性；如果优先行未知且可能改变选择，不回退到后面默认。unique策略若确定命中且另一未知可能改变输出→unknown；所有匹配结果相同也需明确批准允许等价合并，默认多命中conflict。输入/规则上下文受访问限制返回insufficient；不能显示受限规则细节。Rule evaluation是读操作，不能写正式知识、产生真实业务动作或模拟业务实际成功。结果 `matched|not_matched|defaulted|unknown|conflict|not_executable` 加rowRefs、condition trace、result、missing inputs、checked context、evidence refs。Case有明确expected和独立actual observation，不自动将预期当通过。P1黄金案例A/B/C示例值与真实规则隔离。

## 3. 适用性、冲突、符合性

`Applicability`包括contexts/org/product/environment、时间区间[validFrom,validTo)、explicit expression。约束维度缺失→unknown，非匹配→not_applicable；多条适用规范互斥同business scenario→conflict。范围采用AND，列表OR；没有条件表示该定义明确声明unrestricted，不把导入缺字段自动补当天或环境；缺关键上下文提示用户而非默认production。若版本生效日在未来，读取固定asOf；历史读取按baseline发布时间默认asOf（用户可显式指定），权限始终当前。规则冲突能确定性检查的比较范围、同属性和相交条件；复杂业务语义进入review或issue，不宣称可完全自动发现所有矛盾。

`Conformance`必须绑定 exact normativeRevision、observedRevision、build/commit、environment、contextHash、case/test result refs、source evidence digest、verification method/actor/time。以结构化输入、预期/actual比较（case semantics相同、版本和环境一致）生成conformant/divergent/insufficient；不可自动判定的由独立QA写有证据的结论。读取时先重算上述指纹并验证权限、目标修订与当前快照、运行revision和证据状态；变动/撤回→stale；缺必需资料→insufficient；明确矛盾→divergent，不使用旧props.conformance.status。可呈现历史结论但显式历史上下文；观察不是目标，代码回退不是知识基线回退。

## 4. 内容契约：结构化信息而非一堆必填表单

registry 中每type选择profile（project, vocabulary, requirement, rule, flow, design, api, data, observation, case, source, decision, operation）。`ContentCheck`分三层：

1. 确定性结构：验证schema、required/unknown slot、ID refs、引用精确、权限、形状、行/分支、来源、scope、类型谓词允许端点。missing critical字段标blocking；自然句未知允许draft但不得批准相关规范。没有填入“根据规则处理”作为有效判断。语义字段使用`contentBlocks`（stable blockId、kind=paragraph/table/list/notice、text/columns/rows、revisionRefs）；渲染不用硬编码HTML/内部ID。Rule结构字段由业务权威维护，表格从行生成，避免同一explanation塞进条件和判断两列。
2. 语义审阅（真实LLM可辅助）：根据type profile及P1.0 04定义检查需求混入机制、规则判断欠缺、目标和观察混淆、重复、未知、与批准知识冲突。模型返回结构化issues：location/blockId、criterion、severity、explanation、sourceRefs、suggestedRevision；无法定量证明的标need_review。模型报告“通过”不是人批准或事实verified。对外部模型不上传无权/未许可source，引用必须服务端解析到允许的精确revision；输入中的prompt不作为工具指令。
3. 认知验收：真人/独立Agent用批准规则判断新案例，查来源和反例；测试定义见AT-P01..14。拒绝以长度/完整度分数/出现关键字做质量证明。结果 `satisfied|missing|contradictory|unverified|not_applicable`+理由＋证据，不是百分比。

## 5. 授权阅读/组合算法（核心）

`BuildReadingPlan(ReadContext, rootId, goal, profile, depthToken, limit)`：先解析project、baseline、当前ACL，根通过才继续；基线版本为空时published选一次current指针，整次读冻结同一revision集。根profile决定计划：Project→定位/范围/主要能力和系统、重要未知；Feature→需求/规则/Design三个Tab；Rule→条件和依据、结果、默认/异常和案例；Flow→真实stages顺序/合法edges、guard、目标与结果；Component/API→职责、契约、输入输出、错误、数据、依赖与运行；Term→定义/context/同义/引用规则/属性映射。

按“根→必需语义→可选证据与相关关系”分层加载，收集 direct Rule、Action约束Rule、Flow节点/边/transition guard的Rule、关系及Source。保留Flow局部独立stageId、nodeId、edgeId、条件、回流，检查引用无缺。未授权必要事实导致partial+非泄露提示，不将其当不存在或系统无规则。关系端双授权，原始source单独权限；source不可见仅允许经过治理的独立可公开摘要。只可从可见、适用、当前基线产生知识片段。流程文字按真实edge顺序及分支，不由contains/calls/implements产生执行边。循环标“返回阶段X”；复杂路径分页保留转移和引用，不能通过折叠省掉关键语义。

结果 `ReadingView` 包含 heading,purpose,sections[{key,title,blocks,citations,children}]、essentialUnknowns、resolvedContext、nextCursor/expandRef、completeness`complete|partial`（仅相对本任务）。默认主体只呈现业务目的、可判定规则、例/反例、关键当前差异；深层技术/历史/来源可展开，重复文字按stable semanticRef去重。有同一Rule多处使用时允许链接，不复制内容事实。衍生视图不修改数据；标题/条件/结果字段按信息增量组合。拒绝全库 unlimited；默认根及必要关系最大200个知识refs/page、可选分支50/page；遇到超限关键依赖返回partial+continuation，不能声称完整。权限本身不是可由用户选择查看的“高级开关”。

## 6. 检索与缓存

搜索路径：认证/当前scope→精确baseline membership→候选 `search_document`（title/aliases/tokens、业务术语权重、trigram/FTS）→对每个候选再次授权与适用性→rank+cursor→授权后的摘要。中文先精确词汇/子串，再trigram候选，必要离线分词adapter；真实 CPQ 名词召回评估，不能以英文FTS满足中文。禁止在未授权候选上生成facet数量或向模型返回snippet。历史查询不得使用最新索引; 若索引generation未到b，精确DB回退有界查询或标index_pending，不以旧结果冒充current。cursor签名包含principal、policyEpoch、baseline、filter、rank+id、expiry；权限或版本变化重开分页。缓存仅存当前授权后的DTO或公开技术结构，键含project/principal/epoch/baseline/draft/version/contextHash/purpose/locale；source撤权/变更后强制重验；无权读原raw内容不会被cache放大。作为性能优化不得影响事实正确性。
