# 05 需求、完整影响调查、传播、Task认知上下文与交付

P1.0 06、07、09；PD-22..28/31/32。M08 & M09所有者负责状态与证据；M03/M05/M07提供已有知识；M11连接外部真实调查。

## 1. 用户入口到任务边界

人提供自然语言意图，rootUnit/attachment可选。服务器验证非空、权限、source refs，创建task captured及baseBaseline，记录原话不可变。Agent CS-05读取任务关联知识，提出goal、businessChange/implementationOnly/unknown分类、As-Is/To-Be、业务规则及比较语义候选、候选与实际均标来源；缺关键字段/目标时输出`needs_clarification`，提供给人有证据的推荐和具体待确认问题，而不是预填“明确条件下产生目标结果”。任务语义合同只保存差异与精确current/target refs，不复制正式规则。人反馈不直接改既有规则，只形成Proposal/Decision。以下五类变化为固定语义 `add/revise/retire/preserve/revalidate`。任何字段增减，首先保持原始业务目标；若没有等价替代事实才提出规则变更并请求Owner批准。

### 影响遍历具体约束

从物理字段F反向`mapsTo`找属性A、反向`usesFact`找所有Rule R、正向`constrains`找行为，反向`implements`找具体机制，正向`satisfies`/`refines`找原目标，反向`validates`找验收；技术对象的`reads/writes/calls`允许反向找caller并沿有据数据流继续。从业务规则变化起则正向约束/实现与上下游需求，同时复核其他适用规则优先级和共享语义。`contains`、generic dependsOn、同名不作为必改传播，只提供风险线索；每条path保留edge ID和revision，不把路径压平成“影响很多”。查询以当前baseline和endpoint权限为准；按任务风险动态扩展，不以固定3层或遍历全项目为完整。初始每个Job最大500候选、1000边，条件/时长/工具预算超过时checkpoint+continuation或partial；关键未完成调查阻断closure。规则变化可能跨多个业务目标，不能只查直接字段引用。

### 实际调查合同

平台不声称有通用万能源码分析器；提供真实 Agent 调查入口：本地执行端接收Task/Context/有权repo scope，调用语言/仓库的工具（.NET可用`rg`、Roslyn分析、SQL脚本、测试、运行证据；其他语言由外部Agent选择）。执行端保存真实commit/branch、tool callId、命令摘要、exitCode、locator/path/blob hash、artifact hash、开始/结束、覆盖/未查范围；凭据与敏感原文不进通用日志。真实工具证据可由独立CI或受控执行代理身份签出；普通模型自行撰写摘要标reconstructed，不能作为已执行工具记录。对动态SQL、反射、外部调用及运行期配置，要求查询实际配置/运行日志或明确未知；没有repo不影响平台候选能力，但不能传递“已完成调查”状态。人工提供调查结果也须证据及author角色，AI不能伪造实际检查。

### 字段变化样例（非CPQ批准事实）

EX-FIELD-NAME承载EX-ATTR-NAME，`mapsTo`，R1用其判断有名称分支、R2判断无名称分支、R3重复校验；共同约束EX-ACT-APPLY与EX-ACT-CHECK满足EX-REQ-MATCH。不准删除F后顺手删除R1/R2。先比较替代字段或派生事实对旧新输入的等价性；若仅物理重命名，修订mapping、所有read/write/caller、迁移兼容和测试，R1/R2/R3保持但revalidate。若从此无法得到名称存在事实，必须列出受影响规则、产品结果、候选新匹配方式和风险，经业务Owner批准足够规则及案例的变更组，原目标不能自动删除。实现测试新旧行为，上一版本需兼容时双读/回填/切换有明确结束条件；知识中保留迁移和旧版本来源。此样例使用P1.0 EX黄金数据，不把真实CPQ的字段比较组合编造出来。

## 3. Task Context 和版本失效

Task过程 `captured→investigating→needs_decision→ready→implementing→verifying→awaiting_knowledge→ready_for_acceptance→completed`，另`blocked/cancelled`；不允许任意PATCH状态。根据实际记录触发事件。approved业务规范不等于代码完成；部署与知识独立状态显示。TaskContext immutable body includes projectId/taskId/target & preserve, baseline, scopeKey, revisions, required rule/attr/flow refs, exact evidence, impacts, design ownership/constraints, approvals, acceptance, due evidence, knowledge requirements, policyEpoch, contractDigest，必要未知及phase `candidate/executable`。生成时验证所有必需refs和当前主体；对另一个主体获取时再次计算当前权限，任何关键refs不可读则不返回完整正文，也不让部分合同可执行。版本变化：发布新的B、policyEpoch或实际source/build改变，查context_dependency的unit/observed/decision matches，标needs_revalidation并阻断新的执行/closure；已证明范围不受影响的仍可根据新baseline重建有效context，不能把所有工作因无关知识更新强制取消。长任务定期heartbeat检查同一context和fencing令牌，旧结果仅记录为stale evidence，不能更新当前提案/验收。

## 4. 交付门槛函数

`CheckClosure(taskId, contextId)`实时生成：targetCheck、preserveCheck、impactCheck、codeEvidenceCheck、testCheck、knowledgeCheck、deploymentCheck、authorization/approval check、unresolved issues。`complete` iff (1)适用目标已经正式批准且Context仍有效、(2)业务目标正反边界与回归实际证据通过、(3)所有required影响已经交付验证，no_change有明确证据，关键potential/unknown已处置，(4)职责/接口/权限/数据/兼容未被破坏，(5)实际CI Manifest对应代码和测试，(6)知识修订批准发布/无关键知识债，部署对账满足目标环境（纯知识任务可显式non_applicable并有授权原因），(7)有权独立验收。否则blocked或ready_for_acceptance（前置全部满足待人确认），合法紧急例外显示delivered_with_debt、owner/deadline/fixTask，不标complete。每个check返回status、evidenceRef、critical、reason、nextAction，默认显示少量主要问题；不能用户自己切换状态跳过检查。

独立QA按照P1“你说哪两个参数不是全部边界”逆向调查，先阅读需求与保持规则再看diff，至少检查所有已知相关入口、重复路径、旧兼容、责任归属、数据/异常、业务效果，判断缺证据即unknown。技术等价清理（A UNION B ≡ B）须核对集合/重复、多列投影、NULL、权限、分页排序、错误和副作用，才能授权内收敛。用户最终只需审核有意义的业务/工程结论，而非填写影响表。遗留问题均有可追溯owner、处置和影响；原任务阻断不得隐藏。
